# 交易系统技术能力：项目覆盖与待验收清单

本文按业务正确性、低延迟、异构计算和交付治理四个维度整理项目覆盖范围。
每个条目区分可运行证据、设计方案与待目标环境验证的工作，供代码阅读、架构评审和实施规划使用。

## 一、范围与证据等级

FinCore 的基线是交易全链路、资金正确性、故障恢复、有界并发、团队治理与受控 AI 应用。
高并发不自动证明微秒低延迟，方案完整也不代表已在生产环境验收。

| 标识 | 含义 |
|---|---|
| VERIFIED | 当前源码、自动化测试或确定性实验直接验证 |
| OBSERVED | 指定版本、硬件及有限负载下的实测；不能外推为生产容量 |
| DEMO | 可评审的架构、规则模型或故障流程 |
| POC | 待目标硬件、数据规模或外部协议环境验证 |
| OWNER | 须由对应领域负责人实施并完成专项验收 |

同一领域可以同时包含多个等级；验收应细化到具体代码、指标与运行环境，不能以领域标题一概标记完成。

| 系统领域 | 已有实现或材料 | 待补齐的生产化证据 | 当前边界 |

| 交易与资金可靠性 | 撮合、结算、幂等、账本、对账、Fencing 和故障测试 | 目标业务规则、真实资金审计、目标容量及灾备 | VERIFIED；不是生产资产平台 |
| 入口与高并发 | 有界 Lane、虚拟线程、连接池、批量与背压配置 | 热点倾斜、长稳、跨实例容量和过载恢复指标 | VERIFIED + POC |
| Java/C++ 撮合 | 独立双语言代码、Golden、差分与有限实测 | 持久化资金协议、影子流量、状态迁移与端到端压测 | VERIFIED + OBSERVED；仅隔离内存实验 |
| 低延迟全链路 | 主路径/控制面/恢复面及七类延迟口径 | 目标网卡到应用的分段时间戳与 P99.9 数据 | DEMO + POC |
| CPU/Cache/NUMA | 亲和、IRQ、缓存、伪共享、页故障、TLB 和频率方案 | 目标硬件 A/B、计数器、尾延迟与恢复测试 | DEMO + POC |
| 网络/时钟/FPGA | RSS/RPS/RFS/XPS、DPDK、PTP、硬件时间戳与安全慢路设计 | 网卡/驱动/板卡实现、时钟误差预算、旁路恢复 | DEMO + OWNER |
| 行情与市场协议 | 序号缺口、快照恢复、会话和回报的确定性模型 | 真实 Feed/FIX 认证、录包回放及断线补发 | VERIFIED + POC |
| 合约与数字资产 | 风险模型、资金费、强平、重组和提现身份实验 | 完整仓位账本、强平成交闭环、真实链与托管接入 | VERIFIED + POC |
| 研究计算 | 点时数据、回测陷阱、血缘、容量和归因方案 | 真实数据集、实盘偏差、复现与数据授权审计 | DEMO |
| AI/GPU | AI 治理与 GPU 适用矩阵、数据供应/调度/TCO 方案 | GPU 批计算、H2D/Kernel/通信剖析和 CPU 回退 | DEMO + POC |
| 故障恢复 | 交易、账务、旧主、重复消息与对账演练 | 新硬件路径及跨地域 RTO/RPO 证明 | VERIFIED + POC |
| 团队交付 | 职责、质量门、值班、产品运营协同和技术治理 | 对目标团队形成实际排班、签字与事故闭环 | DEMO |
| 投资与容量 | ROI/FinOps、阶段门、成本敏感性和停止条件 | 真实业务归因、预算批准及观察窗口复盘 | DEMO |

## 三、关键工程边界

### 1. Java 高并发不是 HFT 微秒热路径的替代证据

有界 Lane、虚拟线程、Hikari、Kafka、G1/ZGC 和 JFR 支持过载治理与运行时分析。
C++ 单写订单簿、DPDK、FPGA 或亚微秒链路必须使用自己的目标环境数据验收。

### 2. CPU 优化需要数据定位

低延迟优化覆盖 queue—IRQ—core—thread 亲和、NUMA 内存位置、cache line、页故障、TLB、
频率、电源模式、超线程、JIT/编译器和性能计数器。每项变更需要同口径基线、P99.9 A/B 数据与副作用记录。

### 3. GPU 不默认进入逐笔交易热路径

训练、批量推理、Monte Carlo 和矩阵计算可能适合 GPU；单笔订单状态机、数据库事务和微秒小任务
容易受传输、启动与 batch 等待限制。先测数据供应、H2D、Kernel、通信与排队，再决定硬件投入。

### 4. 优化不得绕过资金与恢复协议

专用核心、DPDK 和 FPGA 必须保留录包、版本、计数器、单一发单权威、安全慢路、Shadow 与外部对账。
出现状态未知、输出可疑或所有者冲突时，系统应能停止风险扩张并恢复权威状态。

## 四、下一阶段验收顺序

1. 锁定目标业务范围、规则合同、延迟起止点和资源预算。
2. 在相同语义与硬件条件下复现基线，保留输入、版本、原始样本和未测项。
3. 实现目标方案的资金、持久化、回报与故障恢复协议，逐项验证失败路径。
4. 使用无账务权限的 Shadow 和代表性流量检查差异，验证长稳及故障恢复。
5. 仅在正确性、性能、运行保障和业务收益共同达标后，实施有限范围变更。
