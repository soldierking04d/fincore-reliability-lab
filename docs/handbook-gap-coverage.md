# 交易系统技术能力：项目覆盖与缺口清单

本文按交易可靠性、低延迟、异构计算和交付治理整理项目覆盖与待验收范围。
各项区分已有代码、设计方案与专项验证，不将设计和有限实验标为生产实现。

## 一、审计结论

FinCore 原先已经较完整地证明交易全链路、资金正确性、故障恢复、高并发、团队治理和 AI 受控落地，但容易让
读者把“高并发”误认为“低延迟”。这次补齐后，项目把能力拆成三层：

1. **已有代码证明：** Java 交易可靠性、资金账本、有界并发、Outbox、Fencing、对账和自动测试；
2. **已有架构与演示：** 低延迟全链路、CPU/网络/FPGA/GPU 决策、研究平台和故障推演；
3. **明确专项边界：** C++、DPDK、FPGA RTL、GPU 集群和国内柜台协议仍需目标硬件及领域 owner 验证。

## 三、最关键的边界纠正

### 1. Java 高并发不能直接证明 HFT 微秒热路径

当前项目的有界 Lane、虚拟线程、Hikari、Kafka、G1/ZGC 和 JFR 能证明过载治理与运行时判断能力；它不能
证明 C++ 单写订单簿、DPDK、FPGA 或亚微秒链路已经生产落地。网站与文档必须同时展示已有能力和升级路径。

### 2. CPU 优化不能只写“减少对象和线程”

真正的低延迟 CPU 体系还要覆盖 queue—IRQ—core—thread 亲和、NUMA 内存位置、cache line、页故障、TLB、
频率/电源模式、超线程、JIT/编译器和性能计数器。每项都必须有基线和 P99.9 A/B 数据。

### 3. GPU 不属于默认交易热路径

GPU 适合训练、批量推理、Monte Carlo、因子矩阵和向量回测。单笔订单状态机、数据库事务和微秒小任务通常受
传输、启动和 batch 等待限制。技术负责人应先测数据供应、H2D、kernel、通信和排队，再决定加卡。

### 4. 硬件优化不能牺牲恢复能力

FPGA、DPDK 和专用核心如果没有录包、计数器、版本、单一发单权威、安全慢路径、shadow 和外部对账，会把
局部延迟收益换成不可恢复风险。任何硬件路径都必须有故障演练和退出条件。
