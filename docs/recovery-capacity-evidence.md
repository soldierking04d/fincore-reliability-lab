# 第三阶段：容量与恢复证据

## 结论边界

本阶段回答四个具体问题：有限并发通过完整入口后能否全部交割；Broker 暂停故障后待处理成交能否恢复；数据库备份是否真的能还原；消息日志从容器写层迁入持久卷并重建 Broker 后，消息与消费位点是否保留。

这些检查都在 GitHub CI 临时容器中执行。它们是可复验的工程证据，不是 4 核云服务器的持续吞吐承诺，不代表多 Broker、跨机房或生产灾备。

## 固定并发验收

- 预先创建 64 个互相隔离的市场以及买卖双方模拟账户。
- 16 个并发工作线程经真实 HTTP 接口和有界 Lane 提交 128 张订单。
- 等待 64 笔成交全部经 Outbox、Kafka 和有围栏 Worker 完成双资产交割。
- 对 256 个资产账户分别重算余额、不可变账本、预占、在途与资金审计。
- 报告实际耗时、接受订单/秒、完成交割/秒、HTTP P95/P99、GC 累计耗时增量、队列、连接池和 CPU 采样；不预填好看的数字。

若任一请求拒绝、超时或业务返回不完整，测试直接失败，不自动重试写请求，也不会生成一份“零失败”的成功报告。

## Broker 暂停故障恢复

先停止本测试的消费者，让一笔成交通知由 Outbox 发布并确认资金留在 `PENDING`；再暂停并恢复测试 Broker，等待管理接口可用后恢复消费者。验收要求：

1. 原成交最终为 `SETTLED`；
2. 重复投递创建 Inbox 证据，但只有两笔按资产平衡的账本事务；
3. 买卖双方两种资产余额精确一致，全部账户对账无差异。

这证明客户端和业务消费者可以跨一次 Broker 不可用窗口恢复，不把暂停冒充成进程重启。持久卷专项测试会真正停止旧 Broker、用迁移后的卷创建新 Broker，并验证消息、消费组位点和后续写入；两项合并仍不代表多 Broker 副本切换或跨机房灾备。

## PostgreSQL 备份还原

创建并交割新的资金事实，等待 Outbox 清空并停掉测试消费者，然后用 `pg_dump -Fc` 生成一致备份。备份被还原到一个全新的 PostgreSQL 16 容器。源库和恢复库对所有 `public` 表分别比较：

- 行数；
- 按行 JSON 规范排序后的内容摘要；
- 至少存在一条 `SETTLED` 双资产交割。

恢复操作不连接、不清空也不覆盖源数据库。本测试不等于在线恢复、RPO/RTO 或生产灾备认证。

## Kafka 持久卷迁移

专项测试先让 Broker 将十条消息和消费组位点写入容器目录，再停止 Broker，复制一致目录到本测试新建的命名卷。新 Broker 只挂载这个卷启动，并验证：

- 原十条消息仍在；
- 消费组从已提交的 offset 5 恢复，只读到剩余五条；
- 新增第十一条后 end offset 为 11。

测试卷使用 `fincore-ci-kafka-<UUID>` 形式且带隔离标签，只删除本方法刚创建的精确卷，禁止全局 `prune`。

## 服务器实际发现及处理

2026-09-04 只读检查发现：腾讯云 Kafka 4.3.1 容器虽有匿名卷，但运行时管理接口返回的真实日志目录是 `/tmp/kafka-logs`，约 29 MiB；它不在已挂载的 `/var/lib/kafka/data` 卷内。因此过去只能描述为“容器存在卷”，不能据此声称消息已持久化。

迁移脚本要求显式维护窗口和已验收发行包。它会先停止本项目应用写入，记录业务 Topic 位点，停止本项目 Kafka，保存数据库备份、完整消息目录摘要及恢复镜像，再复制到新的显式命名卷。新 Broker 必须使用同一镜像摘要、相同业务 Topic 末端位点，并报告真实日志目录为 `/var/lib/kafka/data`。失败保持应用停止并保留恢复材料，不能用自动放行旧应用换取表面可用。

现网 Kafka 约受限于 0.75 核，历史 cgroup 采样显示有明显节流；单次采样曾为 37.71% 容器 CPU。不能用单个瞬时数值判断扩容。应在实际演示流量下结合 CPU、节流增量、Lag、Outbox 最老待发时长和完成交割速率继续观察，再决定调高配额或拆机。
