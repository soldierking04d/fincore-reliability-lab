# 技术负责人职责全景：从技术正确到组织经营

> 文档层级：总纲。本文件定义职责边界和证据地图，各专题的执行方法见本目录中的概要与详细手册。

## 一、技术负责人究竟对什么负责

技术负责人不是团队里写代码最快的人，也不是所有问题的最终执行者。这个角色的核心责任是：
在业务目标、客户结果、工程质量、运行风险、团队能力和投入成本之间建立一套能够持续工作的
决策系统，并确保关键结果有人负责、能够验证、出现偏差时可以恢复。

在 FinCore 这样的金融可靠性系统中，职责可以归纳为四个维度：

1. **战略**：决定技术往哪里走、为什么投资、哪些债务必须偿还；
2. **工程**：保证架构、交付、质量、安全、数据和可靠性达到业务要求；
3. **组织**：建立人员梯队，完成招聘、培养、反馈、绩效、授权和接班；
4. **经营**：理解产品、运营、客户、成本、供应商和管理层需要的结果。

技术负责人可以把执行职责分给架构师、领域负责人、交付经理、安全人员或 SRE，但不能把最终
结果变成无人负责的灰色地带。

## 二、十三类职责及最低证据

| 维度 | 职责 | 技术负责人必须回答的问题 | 最低可验证证据 |
|---|---|---|---|
| 战略 | 技术战略 | 下一年最重要的业务变化会要求技术发生什么变化 | 年度技术主题、季度路线图、投资假设 |
| 战略 | 架构治理 | 哪些决定跨团队、难回滚或影响长期成本 | 架构原则、ADR、评审记录、淘汰计划 |
| 战略 | 技术债治理 | 哪些债务正在增加事故、交付或人员风险 | 技术债台账、利息指标、偿还顺序 |
| 工程 | 交付治理 | 团队是否稳定交付真正的业务结果 | 里程碑、依赖、DORA 指标、验收记录 |
| 工程 | 质量工程 | 测试是否覆盖最危险的失败路径 | 质量策略、风险测试、缺陷逃逸和门禁 |
| 工程 | 安全合规 | 权限、密钥、依赖和数据风险是否被持续控制 | 威胁模型、控制矩阵、漏洞和审计记录 |
| 工程 | 可靠性 | 服务对业务承诺什么，承诺被破坏后怎么办 | SLI/SLO、错误预算、值班和灾备证据 |
| 组织 | 组织设计 | 现有人员结构能否支持未来目标 | 领域责任图、岗位与能力缺口、继任计划 |
| 组织 | 人才全周期 | 如何招到、培养、评价、留住并安全交接人才 | 招聘评分卡、90 天计划、绩效和离职清单 |
| 组织 | 团队健康 | 团队是否敢暴露风险，值班和关键人负担是否可持续 | 1:1 主题、健康信号、负担与留任行动 |
| 经营 | 产品与客户 | 技术投入解决了什么用户问题 | 产品指标、客户反馈、支持问题和复盘 |
| 经营 | 成本与供应商 | 每一项技术成本是否有业务价值和退出方案 | 预算、预测、单位成本、供应商评分卡 |
| 经营 | 高层沟通 | 管理层能否基于事实完成范围、成本和风险取舍 | 一页状态、决策请求、风险趋势和承诺 |

## 三、RACI：负责人不等于亲自完成一切

下面是八人左右团队的参考分工。`A` 表示最终负责，`R` 表示直接执行，`C` 表示参与决策，`I`
表示需要同步。实际团队可以合并角色，但不能删除责任。

| 工作 | 技术负责人 | 领域负责人 | 产品 | 交付/项目 | 安全/SRE | 运营/支持 |
|---|---:|---:|---:|---:|---:|---:|
| 技术路线图和架构原则 | A | R | C | C | C | I |
| 需求范围和业务验收 | C | C | A/R | R | I | C |
| 高风险设计和技术债 | A | R | C | C | C | I |
| 发布、SLO 和灾备 | A | R | I | C | R | C |
| 安全与数据控制 | A | R | C | I | R | I |
| 人员梯队和绩效反馈 | A/R | C | I | I | I | I |
| 客户事故和外部更新 | A | R | C | C | C | R |
| 技术预算与供应商 | A | C | C | R | C | I |

## 四、决策边界

技术负责人必须亲自参与以下决定：

- 可能破坏资金正确性、客户资产、隐私或监管要求的变更；
- 跨团队且难以回滚的架构选择；
- 需要牺牲交付范围、稳定性、成本或安全其中一项的取舍；
- 重大事故的恢复确认和对外技术口径；
- 关键人员任用、绩效结论、继任与长期能力投资；
- 超出既定预算、引入长期锁定或缺少退出方案的供应商决定。

以下工作应授权给已经具备证据的负责人：

- 既有架构约束内的常规设计和代码评审；
- 满足门禁的低风险发布和回滚；
- 已有手册覆盖的告警处置；
- 常规需求拆分、测试安排和运行数据分析。

如果技术负责人长期亲自审批所有修改、参加所有会议、处理所有告警，说明职责系统没有建立，
不是负责人“责任心强”。

## 五、技术负责人仪表盘

仪表盘不追求指标数量，而追求每个信号都有触发动作。

| 领域 | 负责人每月最少查看的信号 | 触发动作示例 |
|---|---|---|
| 业务 | 交易成功、资金及时性、投诉与人工处理 | 业务结果恶化时暂停扩量并重排路线图 |
| 交付 | 交付周期、变更失败、返工和依赖等待 | 连续两月恶化时减少并行项目并修复流程 |
| 可靠性 | SLO、错误预算、告警、恢复时间和重复事故 | 预算消耗过快时暂停功能发布并优先稳定性 |
| 安全数据 | 高危漏洞、过期权限、敏感数据访问和审计缺口 | 到期未关闭时升级并限制发布 |
| 组织 | 关键域覆盖、招聘、离职风险、值班负担和团队健康 | 单点或负担超限时调整任务与招聘计划 |
| 经营 | 预算偏差、单位交易成本、供应商 SLA 和锁定风险 | 超预算时先解释业务量与浪费，再决定优化 |

## 六、运行节奏

- **每周**：交付、客户影响、运行风险、跨部门阻塞和需要决定的事项；
- **每月**：质量、SLO、安全、成本、技术债、人员覆盖和改进行动；
- **每季度**：业务方向、技术路线、架构演进、组织能力、预算和供应商；
- **每年**：技术战略、关键岗位规划、重大平台投资、灾备目标和能力退出计划。

每次会议只产生四类结果：决定、负责人、期限、验证方式。没有这些结果的会议应改为异步信息。

## 七、成熟度判断

| 阶段 | 表现 |
|---|---|
| L1 靠人 | 负责人凭经验救火，数据、权限和知识集中在少数人 |
| L2 有流程 | 有文档、会议和负责人，但执行与证据不稳定 |
| L3 可验证 | 关键职责有指标、门禁、演练和可审计记录 |
| L4 可持续 | 团队能在负责人缺席时运行，并用业务结果持续调整机制 |

FinCore 当前在金融正确性、恢复机制、故障演练、团队梯队和跨部门协作方面已经具备 L2～L3
证据；安全合规、正式 SLO/灾备、人才全生命周期、FinOps 和客户支持仍属于需要通过后续实践
逐步形成证据的领域。文档说明目标和方法，不应把计划写成已经完成的生产认证。
