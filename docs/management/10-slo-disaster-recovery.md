# SLO、值班与灾备：把可靠性承诺变成可验证目标

> 文档层级：概要设计。指标口径、错误预算、值班和恢复演练见
> [《SLO、值班和灾备演练实战》](detailed/11-slo-disaster-recovery-playbook.md)。

## 一、监控很多不代表有服务承诺

CPU、QPS、延迟和 Kafka Lag 是系统信号，SLO 必须描述用户或业务真正获得的结果。例如结算
请求被可靠接收、资金在目标时间内完成、查询投影在允许窗口内收敛。技术负责人需要与产品、
运营和业务风险负责人共同确定目标，而不是由研发单独选择一个漂亮数字。

## 二、从关键业务链路建立 SLI

每项服务目标至少定义：

- 事件总量和成功事件的精确口径；
- 数据源、统计窗口和排除条件；
- 目标值和错误预算；
- 预算消耗过快时的动作；
- 负责人和复查频率。

FinCore 可以分别为订单接收、成交持久化、结算最终性、查询新鲜度和对账收敛建立 SLI，不能用
API 返回 200 代替整个资金链路成功。

## 三、错误预算必须改变决定

如果 SLO 被破坏但发布节奏、项目优先级和资源分配没有变化，错误预算只是报表。预算消耗过快
时可以暂停高风险功能、限制活动流量、增加稳定性任务或要求额外评审；预算健康时可以允许合理
试验和更快交付。

## 四、可持续值班

值班体系包括服务目录、告警路由、分级、手册、权限、升级联系人、交接和补偿机制。技术负责人
要持续减少不可行动告警和重复人工操作，并观察夜间打扰是否集中在少数骨干。

值班不是让一个人全天候负责所有系统。每条告警必须对应可执行动作，无动作告警应删除、降级或
转为趋势观察。

## 五、事故管理与复盘

重大事故明确指挥、技术处置、业务联络、记录和恢复确认角色。恢复不能只看技术曲线归零，还要
确认资金、客户状态、数据投影和外部口径。复盘关注检测、缓解、沟通和组织条件，行动项需要
负责人、期限和验证证据。

## 六、灾备从业务影响开始

- **RTO**：业务可以承受多长时间不可用；
- **RPO**：业务可以承受多少数据丢失；
- **恢复顺序**：身份、数据库、消息、应用、监控和外部入口如何恢复；
- **恢复边界**：哪些数据可重建，哪些权威数据不能覆盖；
- **证据**：备份能否恢复、恢复后如何验证不变量和业务连续性。

备份任务成功不等于恢复能力。只有在隔离环境实际恢复、运行验证脚本并记录时间和问题，才算
灾备证据。

## 七、负责人指标

- 关键业务链路 SLO 覆盖和错误预算趋势；
- 告警可行动率、夜间打扰和人工处置时长；
- 事故发现、缓解、恢复和业务确认时间；
- 重复事故和逾期复盘行动；
- 备份成功、恢复演练成功和实际 RTO/RPO；
- 关键服务手册、权限和接班人覆盖。
