# 企业技术风险、审计与监管准备实战

## 一、场景：每个专题都知道风险，但没人能回答总体是否可接受

安全知道实验接口和默认凭证，SRE 知道单机部署，研发知道供应链扫描尚未完成，产品知道演示数据
不能代表生产，AI 负责人知道四个用例仍未建立评测集。这些事实如果只存在不同文档里，管理层仍然
无法决定先处理什么、哪些可以限期接受、风险是否叠加。

本手册用统一风险总账和审计证据目录连接这些事实，不虚构已经完成的生产控制。

## 二、风险偏好模板

| 领域 | 偏好示例 | 硬边界 | 需要谁接受 |
|---|---|---|---|
| 客户资金 | 极低 | 重复资金效果、账本不平 | 资金控制 + 业务负责人 |
| 数据隐私 | 极低 | 未授权泄露或原始生产数据进入 AI | 安全/隐私 + 业务负责人 |
| 服务可用 | 低到中 | 依据业务 SLO 与恢复目标 | 服务所有者，重大影响升级 |
| 交付 | 中 | 可回滚、无客户损失的延期 | 产品 + 技术负责人 |
| 成本 | 中 | 预算阈值和必要风险保护 | 预算所有者 |
| 试验 | 中到高 | 仅限隔离、可撤销和无真实客户影响 | 试验负责人 + 技术负责人 |

真实偏好需要组织批准；本表只展示 FinCore 的判断方法。

## 三、风险登记实例

机器总账 [`governance/risks.yaml`](../../../governance/risks.yaml) 已登记当前可证明的主要风险，包括：

- `lab` Profile 或实验接口被错误暴露；
- 演示默认凭证被误用到生产；
- 单机公网演示造成可用性和容量单点；
- SBOM、签名和依赖扫描尚未形成完整证据；
- 回放、遥测和权威业务指标可能被误读；
- 规划中的 AI 用例缺少脱敏评测集；
- 管理文档和运行手册随系统变化而过期。

风险不是缺陷列表。每项都连接业务影响、控制、剩余风险、负责人、期限和复查。

## 四、风险描述和评分

### 合格描述

> 由于公网演示与实验 Profile 的边界依赖配置，如果部署时错误打开实验接口，未经授权的调用方可能
> 注入故障或触发高负载，导致服务不可用或产生误导证据。

### 不合格描述

> Lab 接口风险很高。

评分采用概率 1—5 × 影响 1—5，只用于排序，不替代硬边界。硬边界风险即使概率低，也不能用其他
低风险项目的平均分抵消。

## 五、处置策略

- **Avoid**：取消产生不可接受风险的设计或权限；
- **Reduce**：通过预防、检测、响应和恢复控制降低概率或影响；
- **Transfer**：通过合同或保险转移部分损失，但责任和客户影响仍需治理；
- **Accept**：在权限范围内接受剩余风险，明确理由、补偿控制和到期；
- **Close**：验证风险场景已消除或不再适用，并保留证据。

风险负责人推动处置，接受人承担剩余风险，两者可以不同。

## 六、控制证据目录

[`governance/audit-evidence.yaml`](../../../governance/audit-evidence.yaml) 记录每项控制：

```text
controlId / objective / owner / frequency
linkedRisks / linkedServices
testMethod / evidence
status / lastVerified / nextReview
retention / limitations
```

例如“结算幂等”由数据库唯一键、重复投递测试和场景报告共同证明；它不能证明生产 RBAC、密钥管理
或真实灾备已经完成。

## 七、风险接受记录

```text
风险编号：
当前控制和证据：
剩余概率与影响：
为什么暂不能继续降低：
业务影响和最坏情况：
补偿控制：
接受人和权限依据：
到期日期：
复查触发条件：
```

资金硬边界、未经授权敏感数据泄露和伪造审计证据不得由普通项目负责人接受。

## 八、审计请求流程

```text
接收请求
  → 确认范围、依据、期限和敏感等级
  → 映射控制与证据所有者
  → 从证据目录提取，不临时修改原始记录
  → 独立复核范围和局限
  → 安全交付并记录接收
  → 发现项进入整改总账
```

对外材料必须区分实验、计划、已实施和生产验证，不能为满足审计问题临时把目标状态写成现状。

## 九、监管变化案例

假设新要求需要缩短高危漏洞处置时间并提供供应链来源证明：

1. 合规负责人记录要求、生效日期和适用业务；
2. 技术负责人映射依赖、构建、制品、供应商和现有 SBOM 控制；
3. 明确缺口：扫描、签名、来源保存和例外流程；
4. 建立分阶段计划、负责人、预算和临时控制；
5. 运行验证并把证据进入目录；
6. 独立复核后关闭发现项。

## 十、发现项整改

| 字段 | 内容 |
|---|---|
| 发现 | 控制目标与实际证据差异 |
| 严重度 | 客户、资金、数据、运行与监管影响 |
| 临时控制 | 永久修复前如何降低风险 |
| 根因 | 为什么流程、系统或责任允许缺口存在 |
| 永久改进 | 控制、代码、权限、人员和证据变化 |
| 复验 | 谁用什么样本和标准确认有效 |
| 关闭 | 有权负责人批准并保留局限 |

## 十一、月度风险会议

只讨论需要决定的内容：新增高风险、趋势上升、跨域依赖、接受到期、控制失败、审计逾期和需要预算
或范围取舍的事项。已按计划推进且没有变化的条目异步更新。

会议输出只能是：降低、接受、升级、关闭或重新评估，并带负责人、期限和证据。

## 十二、失败模式

- 风险总账变成所有缺陷的副本；
- 只登记固有风险，不记录控制和剩余风险；
- 风险负责人默认成为接受人；
- 接受记录没有到期，永久变成已知问题；
- 审计前临时制造证据；
- 自动测试结果被用来证明人员、权限和生产环境控制；
- 发现项以“提交代码”关闭，没有复验。

## 十三、90 天导入

### 0—30 天

- 合并安全、可靠性、数据、供应商、人员和 AI 风险；
- 确认硬边界、偏好和接受权限；
- 建立控制证据目录。

### 31—60 天

- 复核高风险、到期和共同依赖；
- 演练一次审计请求和一次风险接受；
- 把风险与服务、指标和证据交叉引用。

### 61—90 天

- 对逾期、重复和无证据风险升级；
- 将关键门禁接入 CI 或运行监控；
- 依据真实控制效果调整风险评分和偏好。

## 十四、验收标准

- 风险总账能支持管理层做取舍，不只是记录问题；
- 接受权限、到期和硬边界不可绕过；
- 控制证据可追溯且说明局限；
- 审计请求和发现整改不依赖个人临时准备；
- 当前实现、目标状态和生产认证始终分开。
