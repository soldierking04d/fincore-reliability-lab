# 能力提升实战：把一次项目和事故变成团队资产

> 文档层级：详细实践。重点说明培养任务、验证证据、反馈方式和真实改进结果。

## 一、为什么很多培训没有改变团队表现

一个常见现象是：团队讲过幂等、看过 Kafka、分享过 JVM，但事故发生时仍然有人把服务返回
`200` 当成业务成功，把重复消息简单丢弃，把 GC 讨论变成 G1 与 ZGC 的偏好争论。

原因不是成员没有认真听，而是知识没有经过真实任务验证。团队需要把抽象主题变成可观察问题：

- 重复消息究竟有没有产生第二次资金效果；
- Kafka Lag 上升时业务处于延迟、失败还是错误状态；
- 虚拟线程数量增加后数据库连接是否成为瓶颈；
- 对账修复是否只修改查询投影，还是误伤权威事实；
- 限流以后客户是否得到明确、可重试的结果。

能力提升必须让成员做出判断、承担结果并留下证据。

## 二、案例一：四周掌握“重复消息不重复入账”

### 背景

测试发现团队中多名开发都知道“消费要幂等”，但对 Inbox、messageId、businessKey 和账本事务
之间的关系理解不同。经理不安排一次泛化培训，而是设计一个四周主题。

### 第 1 周：从业务损失开始

产品先说明客户场景：用户已经成交，结算消息因网络重试被投递 17 次。如果系统重复入账，
客户余额和平台资产都会错误；如果系统错误丢弃，客户又可能长时间看不到资金结果。

研发共同定义验证目标：

```text
输入：同一个结算业务并发投递 17 次
允许：消息被重复接收、部分处理返回重复状态
不允许：生成第二个 settlement、第二笔资金变化或不平衡账本
证据：Inbox、settlement_order、ledger_transaction、ledger_entry
```

成员需要回答：为什么只有 Kafka offset 不够？因为 offset 表示消费位置，不是业务唯一性；重平衡、
重放和不同消息都可能绕过这个假设。

### 第 2 周：让成员亲手破坏和修复

在测试分支中临时移除一层幂等保护，运行重复投递测试，观察账本或状态会怎样失败。然后恢复
约束并说明每一层的职责：

- Inbox 防止相同 messageId 重复处理；
- businessKey 防止不同消息包装同一业务；
- 状态 CAS 防止非法重复迁移；
- 数据库唯一约束提供并发下的最后防线；
- 同一事务保证 Inbox、状态、余额和账本一起成功或回滚。

这里的学习证据是失败测试、数据库结果和成员解释，而不是一份培训签到表。

### 第 3 周：换一个人做代码评审

让平时不负责结算的成员评审一段相关改动，要求给出业务风险，而不是格式意见。有效评审意见
例如：

- Inbox 是否在账本事务之前单独提交；
- 异常是否被捕获后返回成功；
- `SUCCESS` 状态是否可能再次执行；
- 重试响应是否误导调用方继续生成新业务键。

领域负责人只补充遗漏，不直接给标准答案。

### 第 4 周：跨角色演练

- 测试负责注入 17 次投递；
- 研发备份负责判断和处置；
- 产品确认客户看到的状态；
- 运营判断是否需要暂停活动；
- 平台观察 Kafka Lag 和数据库连接；
- 最终由非结算负责人核对账本平衡。

验收标准是团队可以从业务影响讲到数据库证据，并且两名以上成员能独立处理，而不是所有问题
仍由原负责人回答。

## 三、案例二：从“会看 CPU”提升为“会判断性能瓶颈”

### 问题表现

活动压测时 CPU 达到 80%，有人建议直接扩容；另有人看到虚拟线程很多，建议切回平台线程；
还有人认为换 ZGC 就能解决延迟。三种建议都缺少完整证据。

### 培养任务

团队选择一个固定到达率的场景，同时观察：

- 请求 QPS 与订单速率；
- 撮合 Lane 队列深度和拒绝数量；
- Hikari 活跃、等待和获取超时；
- Kafka 消费积压与消费者 inflight；
- CPU、JVM Heap、分配速率和 GC Pause；
- P95/P99 和真实业务吞吐。

成员被要求按顺序回答：

1. 业务吞吐是否还在增长；
2. 请求排队发生在入口、Lane、数据库还是 Kafka；
3. CPU 忙在业务计算、锁竞争还是 GC；
4. 增加线程会缓解还是放大下游竞争；
5. 扩容、限流、批处理或代码优化哪一种与证据匹配。

### 一次具体判断示例

观测结果：QPS 从 500 增长到 900，CPU 从 45% 增长到 78%，Hikari 12 个连接全部活跃，等待线程
持续上升；撮合队列不深，GC Pause 仍低于目标。

合理结论：瓶颈首先在数据库并发预算，不是 GC。盲目增加虚拟线程只会增加等待，直接切 ZGC
也不会释放数据库连接。优先动作应是检查事务耗时、锁等待和 SQL 往返，再决定数据库或应用
扩容。

通过这种案例，成员学会从关联指标推理，而不是看到单个数字就给方案。

## 四、案例三：一次对账异常怎样变成团队能力

### 事件

成交同步投影出现：

- `MISSING=1`：权威成交存在，查询投影缺失；
- `MISMATCH=1`：成交存在但价格或数量错误；
- `EXTRA=1`：查询投影存在幽灵成交。

新成员最容易提出“让两边数据相等”的修复，即直接修改权威成交。领域负责人应借此建立团队的
修复边界：权威成交和账本不可为了报表好看而改写；可重建投影进行重建，幽灵投影进入隔离区。

### 能力沉淀

一次事件至少产生四类资产：

1. 代码：修复任务具备 repair key 幂等；
2. 测试：重复修复不会产生第二次效果；
3. 监控：三类差异分别计数；
4. 手册：说明谁可以修复、什么必须冻结复核。

下一名成员通过演练复现三类差异并完成 CLEAN 验证，才说明经验已经被团队掌握。

## 五、建立“能力任务卡”而不是培训清单

每个提升目标可以使用下面的任务卡：

```text
能力主题：根据全链路指标判断性能瓶颈
业务场景：运营活动将订单 QPS 从 200 提升到 1000
责任成员：D
支持者：B、F
周期：4 周

需要完成：
- 解释订单、撮合、Kafka、结算和数据库的指标关系
- 运行一次固定到达率压测
- 定位一个人为制造的瓶颈
- 提出方案并说明为什么不选其他方案
- 把结论写入运行手册

验证证据：
- 压测报告和原始指标
- 方案评审记录
- 演练中独立判断通过
- 一名其他成员可以复用手册完成同样定位

失败条件：
- 只根据单个指标下结论
- 无法说明客户或业务影响
- 优化后没有重新验证
```

## 六、管理者怎样给反馈

### 无效反馈

- “技术深度还不够”；
- “需要更主动”；
- “多从全局考虑”；
- “这次做得不错，继续保持”。

这些表达没有行为、场景和下一步，成员无法行动。

### 有效反馈示例

```text
在周五的结算积压演练中，你在 3 分钟内定位到 Kafka Lag，速度很好。
但你看到消费者恢复后就宣布结束，没有核对 Inbox、账本平衡和最终对账，
这会漏掉“系统恢复但业务结果错误”的情况。

下次请按运行手册完成三层确认：消息积压下降、账本平衡、对账 CLEAN。
下周由你主持一次 17 次重复投递演练，我只做观察，完成后我们再复盘。
```

这段反馈包含场景、有效行为、风险、期望行为和下一次机会，能够直接推动成长。

## 七、一个月度能力复盘样例

### 输入

- 本月三个高风险变更；
- 两次告警和一次故障演练；
- 代码评审中反复出现的问题；
- 产品、运营对信息清晰度的反馈；
- 领域覆盖表变化。

### 讨论

1. 哪些问题是知识缺口，哪些是流程或工具缺口；
2. 哪些成员已经有证据进入下一阶段；
3. 哪些负责人仍然承担过多审批和应急；
4. 下月选择哪一个真实主题；
5. 哪些培训或会议没有产生实际行为变化，应停止。

### 示例结论

```text
发现：三名研发都能解释 Outbox，但只有一人能处理 stuck PROCESSING 状态。
判断：不是理论知识问题，而是缺少恢复任务和权限。
动作：由 D 编写超时回收演练，C 评审，E 验证指标，月底无提示执行。
验收：D 和 E 均能完成恢复，Outbox 事件最终进入 PUBLISHED，且无重复发布。
```

## 八、能力指标如何避免被“做漂亮”

如果要求每人每月分享一次，团队会产生大量低价值分享；如果要求演练次数，可能重复执行同一个
简单脚本。指标必须与结果组合：

| 不充分指标 | 更可靠的组合 |
|---|---|
| 培训 10 小时 | 培训后完成真实任务并通过无提示验证 |
| 分享 4 次 | 分享结论进入代码、测试或运行手册 |
| 演练 3 次 | 演练暴露的问题按期关闭并复验 |
| 文档 20 篇 | 非作者按文档成功完成一次操作 |
| 评审 30 个 PR | 发现并阻止业务或可靠性风险的案例 |

## 九、季度能力主题的完整安排

以“高并发下的正确性”为季度主题：

### 第一个月：理解和测量

- 产品解释活动和用户行为；
- 研发建立业务指标到系统指标的映射；
- 测试完成固定到达率和重复请求场景；
- 成员学会从 QPS、队列、连接池、CPU 和 GC 判断瓶颈。

### 第二个月：交付和评审

- 非领域成员负责一次并发相关改动；
- 领域负责人退到评审角色；
- 团队验证限流、超时和幂等行为；
- 运营准备阶梯放量和暂停策略。

### 第三个月：演练和接管

- 负责人模拟不可用；
- 备份主持高流量、重复消息和 Worker 接管复合演练；
- 产品、运营共同确认业务恢复；
- 复盘后更新指标、权限、手册和下一季度梯队计划。

## 结语

真实能力来自对真实问题的判断和承担。培训可以提供起点，但只有当成员能够把知识用于需求、
代码、运行和跨部门决定，并让其他人复用，项目经历才会变成组织资产。
