# 数据产品、指标口径与数据质量治理实战

## 一、场景：三个页面都显示“成交数”，数字却不一样

事故现场可能同时出现：撮合权威表 60 条成交、查询投影缺失 1 条、监控 Counter 受重启影响、页面
回放曲线显示固定 60。四个数字都可能“来源正确”，但用途、时间窗和权威性不同。

治理目标不是强迫所有数字相等，而是让使用者知道哪个用于资金判断、哪个用于运行趋势、哪个只是
演示，并在出现差异时启动正确流程。

## 二、指标登记卡

机器目录 [`governance/metrics.yaml`](../../../governance/metrics.yaml) 为每个指标保存：

```text
metricId / name / version
purpose / type / unit
owner / steward
definition / source / authority
freshness / qualityRules / thresholds
dimensions / consumers / demoOnly
lastReviewed / nextReview
```

目录中的定义是沟通和校验契约，不替代代码、数据库约束和监控配置。

## 三、权威层级

| 层级 | FinCore 示例 | 可以用于什么 | 不能用于什么 |
|---|---|---|---|
| 权威事实 | 订单、成交、账本、余额 | 资金与审计判断 | 直接为展示方便改写 |
| 一致快照 | 对账查询结果 | 判断某次差异 | 推断快照外的新事务 |
| 派生投影 | trade_projection | 查询和展示 | 替代权威成交 |
| 运行遥测 | Counter、Timer、Gauge | 趋势、告警、容量 | 单独证明资金正确 |
| 演示回放 | 网站固定曲线 | 教学和交互 | 冒充生产采样 |

## 四、核心指标契约示例

### trade_count

- 定义：指定运行和一致快照内权威成交记录数；
- 来源：PostgreSQL 权威成交表；
- 所有者：Matching Lead；
- 质量：非负，和 `unique_trade_sequences` 相等；
- 使用：证明成交唯一和场景结果；
- 禁止：用页面曲线或查询投影计数替代。

### duplicate_settlement_deliveries

- 定义：相同结算业务键被接收的总投递次数；
- 解释：数值大于 1 是故障注入或重投证据，不等于发生多次资金结果；
- 必须配对：`ledger_transactions`、Inbox 去重结果和业务键唯一性；
- 告警：重复投递突然升高需要检查生产者、消费者和网络，不自动回滚资金。

### reconciliation_differences

- 定义：一致快照中 MISSING、MISMATCH、EXTRA 总数；
- 维度：差异类型、运行编号、检测时间、修复状态；
- 硬边界：CLEAN 只能在同一口径重新检查后宣布；
- 历史：修复后保留发现和审计记录，不能只留下最终零值。

## 五、质量规则与动作

| 规则 | 失败含义 | 动作 |
|---|---|---|
| 成交数 = 唯一序列数 | 可能重复序列或统计口径错误 | 阻断结果，检查权威表 |
| 每笔账本借方 = 贷方 | 资金不变量破坏 | 安全否决并升级资金控制 |
| 投影延迟 ≤ 目标 | 查询数据可在承诺内使用 | 超时标记陈旧并降级展示 |
| 指标来源存在 | 结果可追溯 | 无来源禁止进入管理报告 |
| demoOnly 明确 | 不混淆回放与真实采样 | 页面和导出强制标识 |

平均通过率不能掩盖金融硬规则失败。

## 六、数据血缘最小表示

```text
PlaceOrderCommand
  → matching_order / trade
  → outbox_event
  → Kafka settlement event
  → inbox_event / ledger_transaction / ledger_posting
  → trade_projection
  → reconciliation finding
  → scenario report / dashboard metric
```

血缘需要标明权威/派生、事务边界、异步延迟、变换版本和责任人。无需先购买大型平台，先覆盖关键
业务链路和管理指标。

## 七、口径变更案例

产品希望把 `trade_count` 从“成交记录数”改成“成交订单数”。这不是字段重命名，而是业务语义变化：

1. 新建 `filled_order_count_v1`，保留旧指标；
2. 列出网站、报告、告警和评测消费者；
3. 提供相同场景下两个指标的差异解释；
4. 并行运行一个观察窗口；
5. 消费者确认后退出旧用途，不改写历史报告；
6. 更新目录、代码、测试、文档和看板标签。

## 八、数据事故案例

### 事件

查询投影出现 1 条 MISSING、1 条 MISMATCH、1 条 EXTRA，但运营页面把投影当成权威成交。

### 处置

- 标记受影响时间窗和页面结论不可信；
- 从权威成交和一致快照重新确认差异；
- 重建缺失/错值投影，隔离幽灵投影；
- 不修改成交和账本；
- 重新发布结果并记录受影响决策；
- 增加页面来源标签和质量状态。

### 证据

运行编号、快照时间、差异列表、修复审计、重新对账结果和对外修正记录共同组成关闭证据。

## 十、失败模式

- 把数据治理只做成权限和脱敏；
- 同名指标在不同页面使用不同分母；
- 用监控 Counter 证明账本正确；
- 修复后删除差异历史；
- 静默改变口径并回填历史；
- 只有数据团队负责，业务所有者不参与定义。

## 十一、90 天导入

### 0—30 天

- 登记十个以内最关键指标；
- 明确权威、派生、遥测和演示来源；
- 为每个指标指定所有者和技术 Steward。

### 31—60 天

- 为金融硬规则和刷新承诺建立质量检查；
- 画出成交—结算—账本—投影—对账血缘；
- 建立指标变更和数据事故模板。

### 61—90 天

- 把质量状态接入看板和业务验收；
- 演练一次口径变更和一次数据事故；
- 删除无所有者、无消费者或重复指标。

## 十二、验收标准

- 关键数字有统一含义和可追溯来源；
- 数据质量失败会改变展示和决策；
- 数据变更和事故能追踪消费者与历史结论；
- 权威事实不会被派生数据或演示曲线替代；
- 指标目录能够由机器检查并持续复查。
