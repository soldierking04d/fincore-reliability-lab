# 技术雷达、创新组合与组织采用实战

## 一、场景：Java 21、ZGC、Redis、Kubernetes 和 AI 都被称为“下一步”

这些技术解决的问题、证据成熟度和组织成本完全不同。如果没有统一雷达和试验卡，负责人容易把
“值得了解”“演示可行”“可以小范围试用”和“成为生产标准”混成同一个结论。

机器雷达 [`governance/technology-radar.yaml`](../../../governance/technology-radar.yaml) 用 Adopt、
Trial、Assess、Hold 表达 FinCore 当前决策，不做通用技术排行榜。

## 二、雷达条目字段

```text
technologyId / name / category / ring
owner / problem / decision
evidence / risks / constraints
successCriteria / exitCriteria
lastReviewed / nextReview
```

状态变化必须附新证据和决策人。仅更新版本号不等于重新评估。

## 三、FinCore 当前雷达解释

### Adopt

- Java 21：项目运行基线，使用 record、虚拟线程和现代 JVM 能力；
- Spring Boot + MyBatis：应用生命周期、事务编排和显式 SQL 边界；
- PostgreSQL：权威事实、锁、唯一约束和一致快照；
- G1：中小堆默认 GC 基线，有容器堆边界、GC 日志与 JFR；
- Coding Agent 受控评测：只对隔离候选使用，不自动合并。

### Trial

- ZGC：只有目标环境证明 G1 停顿不达标且资源足够时，进行受控对比；
- AI 事故诊断与对账解释：完成脱敏评测集后才能进入只读影子。

### Assess

- Redis：评估是否真正解决跨实例缓存或协调问题，不能替代 PostgreSQL 最终约束；
- 平台自助临时环境：先证明当前环境创建摩擦，再决定投资。

### Hold

- Kubernetes/K3s：当前单体演示规模不足以证明其复杂度收益，暂不作为默认部署路径；
- AI 自主资金写入：违反金融权限硬边界，不进入试验。

## 四、试验卡：ZGC 是否值得采用

```text
问题：目标虚拟机上 G1 p99 停顿是否超过业务保护阈值
基线：相同镜像、堆、负载、数据和观察窗口的 G1 结果
假设：ZGC 降低 p99 停顿且吞吐、CPU、内存和成本可接受
范围：隔离压测，不影响公网真实流量
成功：停顿改善达到预设阈值，业务吞吐和正确性不退化
保护：CPU、RSS、OOM、单位交易成本、账本与对账硬规则
停止：资源超限、正确性失败或改善不足
退出：FINCORE_GC 切回 G1，保留比较报告
```

没有真实基线前，ZGC 保持 Trial 而不是 Adopt。

## 五、试验卡：Redis 是否进入架构

### 需要回答

- 当前瓶颈是否来自数据库读、跨实例协调还是热点锁；
- Redis 故障、一致性和数据过期会产生什么业务结果；
- 哪些数据只是缓存，哪些绝不能脱离 PostgreSQL 权威约束；
- 三年成本、运行能力、监控、备份和退出如何处理。

### 停止条件

- 只减少少量查询但引入双写和一致性风险；
- 团队无法证明失效和回源行为；
- 现有 PostgreSQL 索引、批量或投影优化已解决问题；
- 没有明确消费者和业务收益。

## 六、创新组合看板

| 类型 | 建议容量 | FinCore 示例 | 管理目标 |
|---|---:|---|---|
| 核心优化 | 60%～70% | 可靠性、性能、数据质量 | 保护现有业务 |
| 邻近试验 | 20%～30% | ZGC、平台 Golden Path、只读 AI | 可量化改善 |
| 探索 | 10% 以内 | 新协调或分析方法 | 快速学习与停止 |

比例需要结合业务阶段调整，但必须限制并行试验，避免所有项目都占用相同关键人。

## 七、从 Trial 到 Adopt 的评审

```text
[ ] 业务问题和基线仍然成立
[ ] 结果在代表性环境可重复
[ ] 正确性、安全、数据和合规通过
[ ] 性能、可靠性、成本和容量通过
[ ] 服务目录、SLO、监控和手册就绪
[ ] 团队能独立维护、值班和排障
[ ] 供应商、许可证和锁定已评估
[ ] 迁移、回滚和退出已演练
[ ] 原流程何时关闭已决定
```

任何资金硬否决都直接阻止转化。

## 八、组织采用计划

### 使用者分组

- 试点者：愿意在受控范围反馈；
- 主流使用者：需要稳定路径、说明和支持；
- 高风险角色：需要额外权限、训练和审计；
- 不直接使用但受影响者：产品、运营、支持、审计和管理层。

### 采用旅程

```text
识别任务与基线
  → 小范围试点
  → 任务成功与信任反馈
  → 修复摩擦和失败
  → 扩大并建立支持
  → 关闭旧路径或明确长期并存
  → 验证收益与能力保持
```

培训完成率不是采用结果。真正需要看任务成功、持续使用、人工绕过、下游返工和业务收益。

## 九、AI 采用的特殊控制

- 记录正式工具与 Shadow AI 使用边界；
- 让使用者知道哪些数据不能输入、哪些输出必须复核；
- 观察建议采纳、修改、拒绝和自动化偏见；
- 保留原能力训练，防止团队失去独立判断；
- 模型或供应商变化时重新评测，不静默继承批准。

## 十、收益兑现表

| 目标 | 基线 | 目标 | 保护指标 | 观察窗口 | 决定 |
|---|---:|---:|---|---|---|
| 首次验证耗时 | 待实测 | ≤ 30 分钟 | 门禁不减少 | 4 周 | 扩大/继续/停止 |
| 事故证据汇总 | 待实测 | 降低 30% | 危险建议为 0 | 20 个场景 | 只读影子判断 |
| GC p99 停顿 | G1 实测 | 明确改善阈值 | CPU/RSS/吞吐 | 3 轮压测 | Adopt 或退回 |

没有真实基线的目标必须标记为“待实测”，不能填入漂亮数字冒充收益。

## 十一、退出案例：Kubernetes 保持 Hold

当前项目只有一个公网演示实例，Docker Compose 已满足教学部署。引入 Kubernetes 会增加集群、
网络、存储、权限、监控和升级责任，但没有多团队自助、弹性或多服务调度证据。因此当前决定是：

- 不把 K3s/Kubernetes 作为默认镜像或部署要求；
- 保留容器健康检查、无状态边界和配置外置，为未来迁移留接口；
- 当服务数量、环境数量、团队数量或弹性需求达到明确阈值时重新 Assess；
- 不因已经购买服务器或镜像可选就制造采用理由。

## 十二、失败模式

- 技术雷达变成产品名称收藏；
- 所有新技术都放在 Trial，从不停止；
- PoC 成功后直接进入生产，没有组织门禁；
- 用培训人数证明采用；
- 只统计局部提速，忽略下游返工与审核；
- Hold 没有原因和重新评估条件；
- 退出只停止新增，没有迁移现有依赖。

## 十三、90 天导入

### 0—30 天

- 登记现有关键技术和真实状态；
- 为 ZGC、Redis、平台和 AI 建立试验/评估卡；
- 冻结无所有者、无基线的新技术扩散。

### 31—60 天

- 运行最多两个受控试验；
- 建立采用任务测试和收益表；
- 对 Hold 条目检查是否仍有新增使用。

### 61—90 天

- 做出 Adopt、继续 Trial、Hold 或退出决定；
- 将 Adopt 能力接入服务目录、平台路径和培训；
- 公开失败试验结论，停止无价值投入。

## 十四、验收标准

- 雷达表达组织决策而不是技术流行度；
- 试验有基线、成功、保护、停止和退出；
- 转生产包含平台、人员、成本和运行能力；
- 采用与收益通过任务和业务数据验证；
- Hold 与退出能够阻止创新债务继续增长。
