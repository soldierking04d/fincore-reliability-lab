# 公司内部怎样把 AI 编程助手用到实际研发工作

实施入口已补充为[基于 Claude Code / Codex 的工具无关方案](19-agent-based-development-implementation.md)。本篇保留三场景细节与原有 Cursor 可选配置；不要求公司采用 Cursor，通用规范与任务以 `ai/developer-adoption/common-workflow.md` 和任务包装配器为准。

这套方案从程序员每天的三件事开始：读懂陌生仓库、按现有规范完成小需求、用测试复现并修复一个缺陷。
目标不是让 AI 独立承包项目，而是减少查找和重复编写，把需求判断、关键设计和代码质量的责任留在团队内。
以 Cursor 一类仓库型编程助手为参考；工具的选择不能替代清楚的需求、可运行的测试和认真评审。

## 1. 本项目展示什么，不展示什么

- 仓库定位采用项目中实际存在的调用链：AccountController.summary → AccountService.ledgerSummary → AccountMapper.summarizeLedger。
- 小需求采用隔离的 Java 工单分页参数练习，不接入账户、交易、资金或实际工单服务。
- 缺陷修复采用同一练习中的整数乘法溢出，让失败测试与修复之间存在可检查的因果关系。
- 教学参数和测试数据均为合成样本；这些材料不等于已经调用 Cursor 或真实模型完成了代码生成。
- 演示里的本地校验不等于业务接口、数据库查询、真实邮件或线上系统测试；实际执行情况以对应代码、命令和测试报告为准。
- 本文是团队落地方案及演示讲解，不声称已有投产规模、采用率、节约比例或投资回报。

先看三个具体交付件，就能判断这件事是否对团队有用：

| 公司里的实际问题 | AI 可以辅助的部分 | 人必须确认的交付件 |
| --- | --- | --- |
| 接手一个接口，要跨多个文件才能看懂 | 搜索入口、跟踪调用、整理有出处的说明 | 文件与符号都存在；事实和推断分开 |
| 一个小参数需求，容易漏掉边界和已有约定 | 按明确合同拟定代码与测试草稿 | 行为没有被擅自扩大；异常与兼容性符合约定 |
| “看起来改好了”，却没有证明原因被解决 | 先构造复现，再提出最小修复 | 旧版本按预期失败，新版本通过同一条独立断言 |

## 2. 第一步不是写长提示词，而是补齐仓库上下文

仓库没有稳定说明时，AI 和新同事都会反复猜：哪里是入口、用什么版本、怎么运行测试、哪些约定不能改。
先把现有 README、构建文件、CI 和根目录 AGENTS.md 作为共同来源，不复制出一份很快过时的“AI 专用规范大全”。
本项目已有 AGENTS.md，应保留并引用；新增 Cursor 规则不能覆盖或重写其中的约束。

接到任务后，开发者先填写一张很短的上下文卡：

| 项目 | 需要写清楚的内容 |
| --- | --- |
| 本次任务 | 要解决什么问题；哪些不在范围内 |
| 工作版本 | 分支或提交号；工作区是否已有他人修改 |
| 规范来源 | 根目录 AGENTS.md，以及当前目录适用的补充约定 |
| 代码入口 | 已定位的文件和方法；尚未定位就明确写未知 |
| 构建与测试 | 从实际构建文件和 CI 核实的命令；运行条件是什么 |
| 验收条件 | 输入、输出、异常和不能改变的原行为 |
| 数据边界 | 只使用合成样本；不提供令牌、生产日志和客户数据 |
| 完成证据 | 差异、测试结果、未验证事项、需要人工判断的问题 |

不要一开始把整个仓库、整份日志或历史工单都塞给模型。
先搜索相关文件，再提供最小必要片段；上下文更新后，说明来自哪个版本，防止旧解释被当成现状。

## 3. 场景一：用真实源码解释一条只读调用链

任务是“解释账户账本汇总接口从入口到查询如何工作”，本次只读，不修改任何账户处理代码。
开发者可以要求助手：先读项目规则；列出真实文件和方法；按调用顺序解释；把未知项独立列出；暂不编辑。

本次核对的事实来源如下：

| 源码 | 可直接从代码确认的事实 |
| --- | --- |
| src/main/java/dev/fincore/web/AccountController.java 的 summary | 接收 id，把查询交给 service.ledgerSummary |
| src/main/java/dev/fincore/application/AccountService.java 的 ledgerSummary | 调用 accountMapper.summarizeLedger，组织账户编号、期初余额、当前余额、账本净额及期望余额 |
| src/main/java/dev/fincore/infrastructure/persistence/mapper/AccountMapper.java 的 summarizeLedger | 通过 account 与 ledger_entry 汇总查询得到账本重算结果 |

说明应该同时交代限制：读到这三处，不代表已经检查了完整身份鉴权、异常处理、数据库执行计划或生产运行情况。
例如“这是只读汇总链路”有代码依据；“任何用户只能看自己的账户”不能由这三处调用关系自动推导。
没有找到的控制点应继续查找并标记，不得用“通常框架会处理”填空。

交付物是一页带文件和方法引用的调用说明，不是一张脱离代码的漂亮架构图。
接手开发者抽查入口、一个中间方法和 SQL；如果引用不存在或解释越过证据范围，就退回修正。
这一环节的价值要看“找到并核对正确位置的总时间”，不能只看 AI 出文字的速度。

## 4. 场景二：按明确规范做一个小需求

原始需求：“把工单列表分页参数统一处理一下，关键词两端的空白也处理掉。”
这句话还不能直接开发：非法参数是拒绝还是悄悄纠正？空关键词怎么表示？什么算空白？页码是否从零开始？
AI 可以列出这些未知项，但不能替产品和开发负责人自行决定。

本教学练习采用以下已明确的合同：

- page 为从零开始的整数，必须大于或等于 0；负数明确拒绝，不自动改为 0。
- size 必须在 1 到 200 之间，包含两端；越界明确拒绝，不静默截断。
- 关键词参数在代码中名为 query，为 null 时规范化为空串。
- 去掉 query 两端的 Unicode 空白，判定为 Character.isWhitespace(codePoint) 或 Character.isSpaceChar(codePoint)；保留中间空白。
- 此判定包括不换行空格、窄不换行空格及全角空格，但不删除 U+200B、U+FEFF 等所有不可见字符。
- 偏移量采用 long 计算；本练习不发起数据库查询，也不证明超大页码在数据库中具有可接受的性能。
- 不新增框架或依赖，不改接口鉴权、数据库表、业务流程及其他模块。

参考实现保留 TicketQuery.prepare(int page, int size, String query) 入口，对非法分页抛出 IllegalArgumentException。
拒绝旧有非法参数属于有意收紧行为，不能描述为完全兼容；以后接入接口时，调用方还需给出合适的参数错误响应。

先列测试数据，再讨论代码草稿。以下是合同例子，不是声称已执行的报告：

| 输入 | 必须观察到的结果 |
| --- | --- |
| page=0，size=1，query=null | 参数有效；query 为空串；offset=0 |
| page=2，size=200，query 两端含约定的 Unicode 空白 | 参数有效；只剥离两端；offset=400 |
| page=-1，size=20 | 明确的参数异常；不能输出 page=0 的成功结果 |
| page=0，size=0 或 201 | 明确的参数异常；不能输出 size=1 或 200 的成功结果 |
| query 中间含空格 | 中间空格保持不变，不擅自压缩或删除 |
| query 完全由约定的空白字符组成 | 规范化结果为空串 |

人工评审特别看两个地方：实现有没有把“拒绝”改成“容错”，以及空白处理有没有只满足普通英文空格。
如果团队最终要改变合同，应先改验收条件和测试，再改实现；不能让某个 AI 生成版本反过来成为需求依据。
代码注释解释“为什么保留中间空白、为什么拒绝非法分页”，不必逐行复述显然的赋值操作。

## 5. 场景三：先复现整数溢出，再做最小修复

在合法的 int page 与合法 size 下，乘积仍可能超出 int 范围。
教学数据：page=Integer.MAX_VALUE，即 2147483647；size=200；数学上的 offset 应为 429496729400。
如果先按 int 相乘再赋给 long，溢出已经发生，得到的会是 -200，而不是正确的正偏移量。

最小修复要让乘法本身采用 long 运算，例如 offset = ((long) page) * size。
把整个 int 乘积事后转换为 long 不会修好问题；变量名称、返回类型看起来是 long，也不能证明乘法安全。
这是有意构造的隔离缺陷，不应描述为已发现并修复了项目线上分页事故。

完整验证按以下顺序进行：

1. 人先写清期望值 429496729400 及其数学依据，避免模型自己写实现、自己随意决定答案。
2. 使用固定输入建立测试，针对旧实现断言正确值；确认失败是因为结果错误，而不是编译失败或依赖不可用。
3. 保存旧实现的失败输出与测试版本，保留复现路径。
4. 只改变必要的运算类型，不顺手调整非法参数策略、关键词语义或引入新库。
5. 对同一断言运行单缺陷修复版本，再回归其余用例的实际行为不变；旧版尚未实现的参数拒绝与 Unicode 空白规范化仍然失败，不把它们隐藏。
6. 由另一名开发者或评审者核对表达式和边界推理，不能仅让原生成模型口头宣布“已验证”。

长整数不溢出只证明这个算术问题被处理；它不等于数据库能高效执行深分页，也不等于具备分页快照一致性。
若以后要连接实际查询服务，应另立任务验证数据库参数类型、查询性能和最大可用页码，不偷偷扩大这次练习范围。

## 6. 一次普通研发任务应怎样交接

提出任务的人交付业务目标和可确认的验收条件；开发者负责缩小改动范围，助手生成候选解释、代码和测试草稿。
开发者先自审，再进入团队原有的代码评审与 CI，不为 AI 新设一套繁复的审批链。
评审者看的是需求与代码证据，不是模型的自信程度。

每次交付用同一张简短记录，空项如实写“未执行”或“待确认”：

- 需求版本、工作提交和本次改动范围。
- 修改了哪些文件；为什么需要；哪些关键决定由人确认。
- 测试命令、执行环境、结果和失败原因；不要把“计划运行”写成“测试通过”。
- 哪条测试在旧版本失败、在新版本通过；独立期望值从哪里来。
- 未覆盖的接口、数据库、性能或运行环境；下一步验证由谁负责。
- AI 草稿被直接采用、经修改采用，还是被放弃；人工核对和返工分别花了多久。

测试数量不是覆盖率，生成速度不是交付效率，绿色结果也不能替代需求评审。
尤其要防止助手通过删断言、放宽边界、吞异常或修改期望值，让错误实现“通过测试”。

## 7. Cursor 规则怎么配，才不会越写越重

当前官方支持仓库内的 .cursor/rules 项目规则，规则文件使用 .mdc；其中普通 .md 不会作为规则加载。
规则按 alwaysApply、文件匹配或手动引用等方式进入 Agent 上下文；不能假设所有 Cursor 功能都会执行同一套规则。
这里采用一份短的常驻规则，加两份按任务手动引用的规则，避免每次任务塞进不相关长文。[Cursor 官方规则说明](https://cursor.com/docs/rules)

仓库的 `.cursor/rules/` 已放入三个文件；尚未在实际 Cursor 客户端中验证加载，也未为任何公司账号开启策略：

- company-context.mdc：引用已有 AGENTS.md；要求真实源码依据、最小上下文和诚实的验证结论。
- 10-small-change.mdc：手动引用；先确认输入输出与异常，再做限定范围的小改动。
- 20-test-driven-fix.mdc：手动引用；保留先失败、后修复的证据，不改变测试来迎合实现。

迁入其他公司仓库前由团队核对文件内容；保留现有规则和 AGENTS.md，不整目录覆盖。在当前仓库打开 Cursor 后检查常驻规则，按任务手动引用另外两份规则。
规范仍应只有一个权威来源：Java 风格、构建命令等放在已有维护位置，规则引用它，而不是复制另一份。
规则是给助手的指导，不是权限隔离，也不是“有了规则便能取消代码评审”的保证。

## 8. 代码与终端权限：够用即可，不把安全寄托在提示词上

.cursorignore 可以限制索引、直接文件引用及部分 AI 功能对文件的访问，但 Agent 的终端或 MCP 工具仍可能读取这些文件。
因此忽略文件不是安全边界；没有进入仓库的生产密钥，仍可能通过环境变量、外部目录或终端输出意外流入上下文。[Cursor 官方忽略文件说明](https://cursor.com/docs/reference/ignore-file)

试点只使用普通开发权限、隔离工作树和合成数据；不挂载生产密钥，不使用生产数据库连接，不把真实客户日志当示例。
需要终端执行时，检查实际命令及其调用脚本；“运行测试”也可能联网、读环境变量或执行清理步骤。
允许一个命令，不代表允许它任意操作其他项目、上传代码、部署或删除数据。

当前 Cursor 终端执行模式包括 Auto-review、Allowlist 和 Run Everything；不能笼统说“所有终端命令默认逐次由人批准”。
Auto-review 的分类判断不是安全边界；Run Everything 不提供相同的逐项控制。团队应核对实际客户端和管理策略，采用小范围命令许可及适用沙箱，不以一键全自动作为试点默认值。
本地 Agent 模式的设置也不能直接套用到 Cloud Agents。[Cursor 官方运行模式说明](https://cursor.com/docs/agent/security/run-modes)

一次小需求通常只需要读取仓库、编辑指定文件和运行已核实测试；发布、推送、访问外部系统都不应从“帮我写代码”中自动推导。

## 9. 用 AI 编程工具，不等于把 AI 部署在公司内网

IDE 装在本机、代码在本地工作树，不代表提示词和代码上下文留在本机。
Cursor 的 AI 功能涉及向服务端及模型提供方发送上下文；Privacy Mode 改变训练与数据处理承诺，不等于全离线运行。[Cursor 官方隐私说明](https://cursor.com/help/security-and-privacy/privacy)

不能简化为“开隐私模式就什么都不存”：需检查所选模型、滥用检测例外及实际数据条款；自带 API Key 也不等于绕开 Cursor 后端。
选型时记录账号管理方式、允许发送的数据类型、模型和功能范围；不能仅凭产品名字断言符合公司要求。[Cursor 官方数据使用说明](https://cursor.com/data-use)

如果公司的明确要求是源代码不能离开内网，应先核实可以满足该要求的完整技术与合同方案。
不满足就暂不接入这类仓库，或另行评估真正满足边界的方案；不要用 ignore 文件、提示词或“机器是自己的”替代隔离设计。
本方案的演示无需真实客户数据，也无需上线一个会读全公司资料的自动 Agent。

## 10. 四周小组试点：先决定什么值得继续

以下是建议安排，不是已经完成的实施记录。选择一个小组、一个维护良好的仓库和一个明确负责人即可。

| 时间 | 具体工作 | 本周必须留下的产物 |
| --- | --- | --- |
| 第 1 周 | 核实工具的数据与执行设置；整理已有规范；用人工模板完成一批相近小任务作为基线 | 仓库上下文卡、可运行测试入口、任务及总工时记录 |
| 第 2 周 | 只试仓库定位和低风险小需求；开发者逐项检查引用与差异 | 正确与错误案例、采纳修改原因、评审用时 |
| 第 3 周 | 加入有独立断言的缺陷复现；抽样做无 AI 对照；回访合并后的真实问题 | 先失败后修复记录、返工原因、漏检缺陷 |
| 第 4 周 | 汇总净时间、质量和成本；决定扩大、缩小、改规范或暂停 | 继续使用的任务清单、不适用任务、设置和规则调整记录 |

负责人负责安排对照与清理阻塞；开发者记录真实花费；评审者维护质量标准；不要求大家为采用率“凑 AI 任务”。
出现数据边界违规、持续增加评审负担或关键缺陷漏检时，先缩小范围或暂停相关用法，而不是通过放宽质量要求证明试点成功。

## 11. 收益口径：把核对、返工和失败尝试都算进去

按任务类型和复杂度分组比较，不把一次小改动与另一项复杂需求直接比较。
人工基线也应使用相同的模板、搜索工具和已有测试，避免把“整理知识”的收益全部归给模型。
统计所有分配的任务，包括没有采用 AI 草稿、中途放弃和最后仍由人重写的任务。

单个任务的总人时 = 需求澄清 + 仓库理解 + 编写或提示 + 等待期间被占用的时间 + 人工评审 + 测试处理 + 返工。
净时间差 = 可比人工任务总人时 − AI 辅助任务总人时；结果可以为负。
等待时同时在做其他工作，不应再次把整段等待计入人时；机器消耗和费用另记。
还要单独记录工具订阅或调用费用、维护规则与测试样本的工时、培训和安全设置成本，以及合并后的缺陷返工。

可用结果比例、开发者实际采用情况、评审用时和漏检缺陷一起看，不能只报生成行数或补全接受率。
有时间节约并不自动产生现金收益：固定团队省出的时间通常先体现为可用于其他工作的容量，是否带来交付改善还需观察。
没有真实对照数据前，只说明测量方法，不填一个好看的节约百分比。

## 12. 哪些情况应该不用，或先退回普通方法

已有清晰模板、搜索一次就能完成的工作，直接用模板和搜索，未必需要模型。
需求关键条件缺失、规范互相冲突或测试无法运行时，先补齐条件；让 AI 写更多代码只会把问题延后。
接口权限、架构迁移、复杂并发等变化可以让助手辅助查资料和列风险，但不能沿用本小需求练习的验证强度。
重复生成很多相近测试会增加维护负担；优先保留覆盖不同失败原因的有效用例。
同一个模型既生成实现又判定“答案正确”，容易相互迎合；关键期望来自明确合同、人工推导或独立已有测试。
工具、模型或供应商策略变化后，用留存样本回归质量和数据设置，不把上一版本的表现当永久承诺。

真正值得留下的是：开发者更容易找到正确代码，小需求更少漏边界，缺陷修复有可重复证据，而且总评审与返工成本没有反而上升。
