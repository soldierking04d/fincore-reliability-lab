# 技术战略与架构治理实战

## 一、场景：功能很多，但团队说不清下一步为什么做

FinCore 已经完成撮合、结算、Outbox、Fencing、对账修复、监控和故障演练。若后续只是继续增加
中间件、接口和场景，项目会越来越复杂，却不能证明技术负责人能够选择方向。

技术负责人先把未来目标分成三类：

- **公开演示**：访问者能理解、能操作、能看到真实证据；
- **可靠性研究**：失败路径可复现，结论不依赖偶然结果；
- **生产化研究**：明确认证、安全、灾备、容量和合规差距，不伪装成已生产可用。

这三个目标共同决定路线图，而不是由某项新技术决定。

## 二、技术战略一页模板

```text
业务方向：未来 12 个月要支持什么客户、规模和风险等级
当前事实：已有能力、容量、事故、团队和成本证据
核心约束：资金不变量、时间、预算、人员、监管和供应商
技术主题：最多 3～5 项，每项对应一个业务结果
明确不做：本阶段不进入的范围及原因
领先指标：交付过程中的可观察信号
滞后指标：最终业务、客户、可靠性和成本结果
资源分配：人员、预算和外部依赖
复查日期：什么新证据会让路线图改变
```

## 三、FinCore 十二个月路线图示例

这是规划样例，不是已经完成的生产承诺。

| 季度 | 技术主题 | 业务结果 | 交付证据 | 明确不做 |
|---|---|---|---|---|
| Q1 | 身份与实验隔离 | 公网演示不会暴露高风险实验能力 | RBAC 威胁模型、权限测试、环境隔离 | 不接真实账户 |
| Q2 | SLO 与灾备基线 | 能说明可用性目标并证明备份可恢复 | SLI、错误预算、恢复报告 | 不承诺多地域零损失 |
| Q3 | 容量与成本认证 | 知道不同负载下的容量、延迟和单位成本 | 多规格压测、成本曲线、瓶颈结论 | 不用单次峰值宣传 |
| Q4 | 多实例可靠性研究 | 证明故障转移仍守住资金不变量 | 数据库故障、Kafka 重平衡、接管演练 | 不直接上线真实资金 |

## 四、季度容量分配

参考分配不是固定比例，但每类工作必须显式可见：

| 类型 | 参考容量 | 说明 |
|---|---:|---|
| 产品与演示结果 | 35% | 用户能够理解和操作的价值 |
| 可靠性与安全 | 25% | SLO、灾备、权限和故障研究 |
| 技术债与平台 | 20% | 减少重复、人工和长期锁定 |
| 团队能力 | 10% | 接管、培训、工具与文档 |
| 探索空间 | 10% | 小规模验证，不提前承诺 |

当出现重大事故或错误预算快速消耗时，比例可以临时转向稳定性，但要说明何时恢复。

## 五、架构评审实例：是否引入 Redis

### 初始提议

“高并发系统应该有 Redis，把账户余额和订单簿放进去可以更快。”

### 评审问题

1. 当前瓶颈是否已经被测量为读取延迟；
2. Redis 中的数据是权威数据还是可重建投影；
3. 双写失败、乱序和回放如何处理；
4. 新组件增加多少运维、成本和团队能力要求；
5. 如果不用 Redis，索引、批处理或本地有界缓存是否足够；
6. 何时撤销决定，如何迁移数据。

### 当前决定示例

不把资金余额和权威订单状态迁出 PostgreSQL。只有当真实压测证明查询投影成为瓶颈，并且投影
可以从权威数据重建时，才为只读场景验证 Redis。先记录假设，不因为架构图“看起来完整”引入。

## 七、技术债评分

每项按 1～5 分评估：业务影响、事故概率、发生频率、人工时间、交付阻塞、知识单点；再减去修复
成本和风险。评分只是排序输入，不能替代专业判断。

| 技术债 | 利息证据 | 优先级 | 验收 |
|---|---|---:|---|
| 灾备未实际恢复 | 只有备份任务，无恢复时间 | P0 | 隔离环境恢复并通过金融不变量检查 |
| 安全检查只靠人工 | 依赖与制品缺少持续证据 | P0 | 分阶段引入 SBOM 和扫描门禁 |
| Kafka DLT 未完成 | 毒消息处置需要人工判断 | P1 | 审核、重放、审计和幂等测试 |
| 演示文档入口分散 | 访问者理解成本高 | P2 | 网站与 README 使用同一目录 |

## 八、路线图评审会议

季度会议 90 分钟，只讨论：

1. 上季度哪些业务假设被验证或否定；
2. 客户、事故、安全和成本证据发生什么变化；
3. 哪些项目继续、停止、合并或推迟；
4. 未来一个季度的三个最重要结果；
5. 资源、人员和决策缺口；
6. 技术债与探索空间是否被长期挤压。

会后只发布一份路线图和决定记录，不创建多个口径不同的计划。

## 九、失败模式

- 路线图只有功能，没有可靠性、安全、成本和组织能力；
- 每个部门都把自己的事项标为最高优先级；
- 技术负责人用个人偏好替代数据和业务目标；
- ADR 只记录最后选择，不记录被放弃方案和撤销条件；
- 技术债没有利息证据，最终变成无限重构清单；
- 规划完成后从不根据事故、客户和容量数据调整。

## 十、验收标准

- 每项季度主题都有业务结果、保护指标、负责人和停止条件；
- 高风险架构决定可以追溯到证据和复查日期；
- 新项目进入时明确替换的工作；
- 技术债优先级能解释真实利息；
- 团队成员能够说明当前最重要的三个技术结果及原因。
