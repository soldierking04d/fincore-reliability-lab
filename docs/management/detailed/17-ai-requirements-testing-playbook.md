# 内部需求与测试：把“活动邮件预约发送、支持取消”整理成团队能交付的工作

> 本文使用合成需求、计划编号、时间和收件人数据。当前方式是固定模板与本地确定性参考模型，未接入真实 LLM。
> 参考模型用于检查约定的状态和预期，不是业务服务、任务队列或邮件系统测试；不代表功能已开发或投产。

## 1. 起点是一句话，不是一份完整需求

运营提出：“希望活动邮件可以预约发送，也支持取消。”

这句话确定了两个方向：预约、取消。它没有说明什么时候还能取消、取消后哪些邮件不会发送、
能否修改预约时间、怎样处理重复点击和发送失败。直接据此生成几十条测试，仍可能不知道真正要做什么。

本用例中的 AI 候选价值，是帮助团队暴露遗漏、整理已经确认的规则、生成可核对的需求与测试草案。
关键未知由产品与相关人员决定，不由模型自动补成“常规做法”。

## 2. 先准备最少的输入

需要的不是大量资料，而是几份当前有效、彼此能对上的输入：

- 原始业务说明：为什么预约、谁使用、取消要解决什么问题。
- 现有页面或流程说明：现在怎么发邮件，哪些能力已经存在。
- 产品规则：状态定义、时区、权限、失败处理和限制；没有就明确写“待确认”。
- 相关历史问题：重复发送、取消提示误导、改约后仍按旧时间发送等。
- 文档来源、版本和负责人，方便发现冲突时找对人。

缺少页面说明时，不能假设已有“撤回”按钮；缺少接口文档时，不能编造参数和状态码。
资料不足先生成待确认清单，不把没有证据的细节混进正式验收标准。

## 3. 第一份产物：已知与待确认清单

| 已知 | 必须确认，不能自动决定 |
|---|---|
| 运营需要指定未来时间发送 | 使用哪个时区，过去时间如何处理 |
| 需要取消预约 | 发送已经开始时，是拒绝取消，还是停止尚未发送的部分 |
| 页面需要显示结果 | “取消成功”具体表示未开始、部分停止，还是实际撤回 |
| 计划可能发生修改 | 未开始时能否改约，改约如何影响旧任务 |
| 操作可能被重复点击 | 重复请求是否返回同一个结果 |
| 邮件可能发送失败 | 失败是否重试，哪些范围可以重试，谁决定 |

如果帮助文档写“可随时取消”，旧设计写“开始发送后不可取消”，输出应列出两个出处和冲突。
不能挑一个看起来更完整的版本，也不能把两种规则拼成含义不明的新规则。

## 4. 第二份产物：教学产品决策记录

以下是为演示选定的一组 v1 决策，不是某家公司的既有规则，也不是模型自行确认的事实。

| 决策 | v1 教学选择 | 需要谁确认 |
|---|---|---|
| 预约时间 | 用户明确时区，保存可比较的时间；过去时间拒绝 | 产品、研发 |
| 未开始取消 | 状态为 SCHEDULED 时可以取消 | 产品 |
| 发送中取消 | 状态为 SENDING 时拒绝，不声称撤回已发送邮件 | 产品、运营 |
| 未开始改约 | SCHEDULED 可以改到新的未来时间；原预约不得继续生效 | 产品、研发 |
| 重复操作 | 同一请求重试返回原结果；不同内容不得复用同一请求号 | 研发提出，产品与 QA 核对体验 |
| 未确定内容 | 收件人限制、发送失败重试策略等继续保留待决 | 对应负责人 |

规则中的“已开始”由权威状态判断，不能只根据钟表是否过了预约时间猜测。
未确认内容不能进入“已完成需求”，相关测试也不能凭空设定唯一预期。

## 5. 第三份产物：带编号的需求与验收条件

| 需求 | 验收条件 | 关联测试方向 |
|---|---|---|
| REQ-01 预约发送 | AC-01：有效带时区未来时间形成预约；等于现在、过去、缺时区或不存在的日期拒绝 | 正常、时区、时间边界 |
| REQ-02 未开始取消 | AC-02：SCHEDULED → CANCELLED，计划不再允许开始发送 | 正常取消、重复、取消与开始竞争 |
| REQ-03 发送中处理 | AC-03：v1 中 SENDING 的取消被拒绝，原状态与发送事实不改变 | 状态、文案 |
| REQ-04 修改预约 | AC-04：改约成功后仅新版本可开始发送，旧任务不能继续生效 | 改约、旧版本任务、重复修改 |
| REQ-05 重复请求 | AC-05：同请求同内容不产生第二次状态变化；不同内容冲突 | 重复、请求号误用 |

验收条件写用户和系统能观察到的结果，不只写“调用取消接口成功”。
本表是需求草案的目标结构，不说明真实接口、状态存储或任务系统已经实现。

## 6. 一条完整用例：未开始时取消预约

**TC-06，关联 REQ-02 / AC-02，教学需求版本 demo-v1/reject/allow。**

合成测试数据：

```json
{
  "planId": "PLAN-DEMO-001",
  "state": "SCHEDULED",
  "planVersion": 7,
  "scheduledAt": "2026-09-10T02:00:00Z",
  "now": "2026-09-10T01:59:00Z",
  "totalRecipients": 10,
  "requestId": "CANCEL-DEMO-001",
  "expectedVersion": 7,
  "simulatedSentCount": 0
}
```

- **Given / 前提**：计划仍为 SCHEDULED，版本为 7，没有开始发送；当前请求使用上述固定数据。
- **When / 操作**：提交取消，再用完全相同请求号和内容重复提交一次。
- **Then / 预期**：首次结果为 CANCELLED、版本为 8；再次返回同一结果，版本仍为 8。
- **后续检查**：本地参考模型拒绝该已取消计划的“开始发送”动作，模拟发送计数仍为 0。
- **不变条件**：收件人总数不变；重复取消不创建另一份操作效果。
- **记录证据**：输入、需求版本、首次与重复输出、最终状态，以及验证对象标识。

这里的发送计数是参考模型字段，没有发出真实邮件。
真实服务还必须另外验证取消状态、待执行任务和发送组件之间的约束，不能拿本地模型结果代替。

## 7. 不只生成正常路径

| 类别 | 具体检查 | 不能缺少的预期 |
|---|---|---|
| 正常 | 未来时间预约、未开始取消、未开始改约 | 最终状态与生效版本 |
| 边界 | 时间恰在边界、不同时区、新时间已过期 | 按明确时间规则处理，不默默修改输入 |
| 状态 | 对 SENDING、SENT、CANCELLED 发起取消 | 分别对应已确认规则，不统一返回“取消成功” |
| 重复 | 同请求重试；同请求号但不同内容 | 同内容同结果，不同内容明确冲突 |
| 竞争 | 取消与开始发送几乎同时发生 | 只允许一条合法状态路径胜出 |
| 失败 | 结果返回前超时、旧预约任务迟到、发送组件失败 | 明确已知/未知与下一步；未决规则标记待确认 |

对于取消与开始竞争，本地参考模型可以枚举“取消先发生”和“开始先发生”两种顺序。
它不能证明真实多线程、数据库或队列已正确处理竞争；真实并发测试属于后续服务验证。

用例只有步骤、没有预期时不可验收。步骤更多也不代表覆盖更全面。
测试数量不是覆盖率，应核对每条已确认需求、关键状态和已知风险有没有对应证据。

## 8. 研发与 QA 的评审是完成工作，不是给 AI 打分

产品核对规则是否真实确认，运营核对提示是否符合使用场景，研发核对实现约束，QA 核对预期能否判断。
一次正常评审即可，不为草案额外建立多层批准流程。

评审重点是：哪里有未说明的假设、哪里缺失败处理、哪些用例重复、哪些结果无法观察。
最后产出一份收敛后的需求版本和测试清单，而不是保留所有生成文本让团队逐行背负维护成本。

如果同一个模型既生成规则又生成预期，可能把同一错误重复确认。
应使用已确认需求、人工准备的反例和独立参考模型检查；参考模型自身也需要审查，不能自动成为标准答案。

## 9. 执行结果要写验证对象，真实问题要回到需求

每次记录至少包含：需求/用例版本、输入、预期、实际、验证对象、结果、证据和问题编号。
验证对象明确区分“本地参考模型”“业务服务”“真实测试邮件链路”；未执行就写未执行。

例如本地模型通过取消用例，不表示真实任务已撤销。
如果实际集成测试发现改约后旧任务仍发送，应登记缺陷并回到 AC-04 检查遗漏，而不是改预期让结果通过。

修复后保留该失败输入作为回归用例，并核对相同问题是否影响取消或重复操作。
产品发现原需求不清时先修需求版本，再修改实现与测试，不能让测试代码悄悄替产品决定业务规则。

## 10. 需求变化：从拒绝取消到停止尚未发送部分

假设产品把 v1“发送中拒绝取消”改成 v2“停止尚未发送部分，已发送邮件不撤回”。
这不是只改一条提示文案，至少影响以下产物：

- REQ-03 / AC-03：新增已发送与未发送范围、部分停止结果和可观察计数。
- 旧状态测试：原本预期拒绝的用例必须标记只适用于 v1，不能直接当作 v2 回归。
- 新测试数据：例如合成批次 10 人，已发送 3 人；验证只停止剩余 7 人，不声称撤回前 3 人。
- 竞争与失败：停止请求与下一批发送交错、发送回报迟到、重复停止和中途失败。
- 页面与运营说明：不能把“部分停止”显示为全部取消，也不能据此承诺已发送内容失效。

进一步未知包括“正在发出的那一封如何归类”等，仍由产品与研发确认。
本项目参考模型已分别表达这两种教学选择，改变决定后必须重新生成和执行，旧结果不能当作当前结果。
“停止剩余”的模型没有供应商在途请求；真实服务未实现或未验证的部分继续标记未执行，不能只改文档便宣布真实功能通过。

## 11. 容易出现的负面结果

缺少输入时生成看似完整的需求，冲突资料被错误合并，自造验收标准，都可能把返工推迟到开发后期。
大量相似用例会增加评审与维护负担；流畅的文字会掩盖缺少预期和无法观察结果的问题。

因此，每次生成都允许“不够信息”“需要确认”和“删除冗余”。
资料变更后重新核对来源；不要把真实客户信息、内部凭据或未经允许的材料放入外部工具。

## 12. 两周小试点与价值判断

第一周只选这一条需求，整理现有模板和规则，记录人工澄清与测试设计基线，再准备合成反例。
第二周由产品、研发和 QA 使用同一组材料评审草案，记录采纳、改动、遗漏、重复和真实缺陷反馈。

比较的是一整条需求的澄清、评审、测试和返工净工时，并与“模板 + 人工”流程对照，不只看生成速度。
同时记录模型/工具费用、资料维护和额外审查成本；没有真实模型运行时，不填真实调用成本或节约百分比。

如果生成省了时间却增加了更多核对和返工，就缩小范围或停用；如果模板已经足够，也无需引入模型。
最终有价值的是团队拿得到、用得上、能随需求变化维护的产物，而不是生成文字或用例的数量。

## 13. 页面操作与代码位置

1. 在 AI 章节查看原始需求和 B1–B3 教学补充纪要；两个产品问题默认待确认。
2. 点击整理草案，查看 5 组 REQ/AC。保留待决项时也能生成草案，不伪造确定规则。
3. 生成 13 条关联用例，展开查看前提、操作、输入和预期。
4. 两项都未决时，本地参考模型只执行 9 条，另外 4 条阻塞。两项确认后可执行 13 条。
5. 执行结果单独标注验证对象；IT-01～04 的真实队列、外部发送和页面检查没有运行。
6. 改变产品选择，检查影响编号与旧产物过期提示；重新生成、执行。
7. 记录评审意见，下载本次教学 JSON，包含决定、来源、用例、结果及未执行项。
