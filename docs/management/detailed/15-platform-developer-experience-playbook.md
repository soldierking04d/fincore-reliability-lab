# 平台工程、开发者体验与知识治理实战

## 一、场景：新成员需要两天才能运行第一次故障实验

FinCore 仓库已经包含 Java 21、Maven、Docker Compose、PostgreSQL、Kafka、Prometheus、Grafana 和
多个验证脚本。如果新成员仍需反复询问版本、命令、端口、凭证和场景顺序，说明资产存在，但平台
产品没有形成。

本案例目标不是搭建新的门户，而是把“克隆仓库到得到第一份可信证据”做成第一条 Golden Path。

## 二、服务目录

机器目录 [`governance/services.yaml`](../../../governance/services.yaml) 是统一入口。每项至少包含：

```text
serviceId / name / lifecycle
businessCapabilities
owner / deputy / criticality
repositoryPath / dependencies / dataClasses
slo / onCall / runbooks
lastReviewed / nextReview
```

目录变更随代码评审，避免单独门户与仓库事实分叉。负责人离职、服务退役、SLO 或依赖变化时，目录
是必须更新的交付物。

## 三、Golden Path 01：第一次验证

### 用户旅程

```text
检查 Java 21 和 Docker
  → 启动依赖
  → 执行核心验证
  → 执行 Maven 测试
  → 启动完整服务
  → 运行 market-crash-day
  → 打开报告与指标
```

### 成功标准

- 新成员不需要私聊某个骨干；
- 每一步失败都说明原因和下一步，而不是只返回堆栈；
- 30 分钟内获得核心模拟结果；
- 90 分钟内获得完整场景证据，首次下载依赖除外；
- 结果明确区分模拟、容器测试、场景回放和公网运行。

### 保护指标

- 不降低 Java、数据库和 Kafka 版本要求来“让环境能跑”；
- 不跳过安全、架构和 AI 治理门禁；
- 不把默认实验凭证推广为生产配置；
- 不在失败时自动执行破坏性清理。

## 四、Golden Path 02：从变更到反馈

```text
本地约定检查
  → 核心领域模拟
  → Maven 单元与集成测试
  → 公开评测/治理登记检查
  → 构建制品
  → 失败定位链接和责任域
```

CI 的关键体验指标不是“流水线运行了”，而是开发者能否快速判断：哪个业务不变量失败、这是环境
问题还是代码问题、由谁处理、能否安全重试。

建议记录 P50/P95 排队时间、执行时间、失败后第一次修复时间、同类失败重复率和不可行动错误比例。

## 五、平台 SLO 示例

| 旅程 | SLI | 目标示例 | 失败动作 |
|---|---|---|---|
| 代码验证 | 主分支 CI 可运行比例 | 月度 ≥ 99% | 平台故障不计应用变更失败，优先恢复 |
| 反馈 | 提交到首个可行动结果 | P95 ≤ 15 分钟 | 拆分慢任务、治理排队和缓存 |
| 场景运行 | 完整实验成功启动 | ≥ 95% | 标记环境/脚本/业务失败类型 |
| 监控 | 指标可查询且新鲜 | ≥ 99%，延迟 ≤ 2 分钟 | 降级告知并停止依赖指标的结论 |
| 文档 | 关键手册按期复查 | 100% | 过期标记并由所有者整改 |

目标需要真实基线后确认，本表不是生产承诺。

## 六、知识对象登记

关键知识按四类管理：

1. **概念**：架构、不变量、术语和边界；
2. **任务**：启动、发布、回滚、恢复和审计步骤；
3. **决策**：ADR、例外、风险接受和技术雷达；
4. **证据**：测试、演练、指标、报告和审计记录。

每份关键文档增加：所有者、适用服务、最后验证、下次复查、验证方式和替代文档。文档过期后应
在入口处明确显示，而不是等待读者踩坑。

## 七、DevEx 访谈与任务测试

每季度选三到五名不同角色完成实际任务：启动项目、定位一次失败、找到服务负责人、运行一次回滚
或解释一个指标。观察等待、搜索、切换工具、权限和理解错误，不只问“你对平台满意吗”。

访谈输出：

```text
任务：
预期结果：
实际耗时和失败点：
需要人工帮助的位置：
错误反馈是否可行动：
建议删除、自动化或解释的步骤：
负责人和验证日期：
```

## 八、平台需求排序实例

| 候选 | 频率 | 失败损失 | 可复用 | 当前摩擦 | 决定 |
|---|---:|---:|---:|---:|---|
| 一键核心验证 | 高 | 高 | 全员 | 高 | 先完成 |
| 服务目录 | 高 | 高 | 跨角色 | 高 | 同期完成 |
| 自助临时环境 | 中 | 中 | 研发测试 | 中 | 有基线后 Trial |
| 新建综合门户 | 低 | 低 | 未证明 | 中 | 暂缓 |

## 九、失败模式

- 建成新门户却仍要求平台人员处理每张工单；
- 标准路径只覆盖成功情况，失败信息不可行动；
- 平台用应用团队的部署频率证明自己成功；
- 文档数量上涨但没有所有者、使用和新鲜度；
- 为统一而统一，阻止合理的领域扩展；
- 平台成为权限和发布的单点瓶颈。

## 十、90 天导入

### 0—30 天

- 建立服务目录并确认负责人、备份和生命周期；
- 选定第一次验证旅程，记录当前耗时与求助点；
- 为关键手册增加复查和验证字段。

### 31—60 天

- 固化 Golden Path 和明确失败反馈；
- 建立平台 SLI、DevEx 任务测试和需求队列；
- 将服务目录和文档新鲜度接入治理校验。

### 61—90 天

- 对第二条高频旅程复用模式；
- 删除重复工具和失效入口；
- 依据采用、任务成功和业务影响决定下一季度投资。

## 十一、验收标准

- 服务目录可以支持事故、审计、成本和交接；
- 新成员能沿 Golden Path 独立得到可信证据；
- 平台失败反馈可行动且有自己的 SLO；
- 文档新鲜度由所有者和演练证明；
- 平台投资由用户旅程和任务成功决定。
