# 不绑定 Cursor：复用 Claude Code / Codex 的公司研发实施方案

公司不需要自建一个 IDE，也不必重新造一个会读文件、改代码、跑命令的 Agent。
先让开发者使用已有 Claude Code 或 Codex；公司维护同一套任务合同、仓库上下文、可运行验证和结果规范。
工具可以替换，验收标准和代码质量责任不能随工具改变。
下文是建议实施方案；现有 Java 样例是确定性教学对照，不是已执行的真实模型效果评测。
本轮完成共享流程、规则入口、任务包装配与本地候选验证工具；不搭建 worker 平台，不自动调用模型。

## 1. 哪些买现成，哪些由公司维护

| 层次 | 实际得到什么 | 公司仍要负责什么 |
| --- | --- | --- |
| 现成编程 Agent | 复用搜索、编辑、命令执行、上下文与多轮处理能力 | 任务范围、访问权限、验收、评审与费用管理 |
| Agent 的 CLI / SDK | 将既有 Agent 接入脚本，复用其执行能力 | 可靠启动、显式上下文、结果解析、超时及隔离 |
| 直接调用模型 API | 获得推理及所选接口的工具调用能力 | 选择或实现工具执行环境、上下文装配、错误恢复和验证闭环 |

直接调模型 API 不会天然获得一套可维护的公司研发流程；用 Agent SDK 也不必把所有执行能力从零再写一遍。
对当前三个场景，先复用现成 Agent，只有已有产品无法满足的具体集成需求才下沉到 SDK 或模型 API。
订阅账号、脚本认证、可用功能和计费要分别核对，不能把“买了一个账号”理解为任意自动化都已具备权限与额度。
官方已提供 [Codex 非交互入口](https://learn.chatgpt.com/docs/non-interactive-mode) 和 [Claude Code 程序化入口](https://code.claude.com/docs/en/headless)，无需为试点开发新编辑器。

## 2. 公司先沉淀四件小而稳定的交付物

以下名称是建议的任务包结构，不表示已经接入公司的业务系统：

- task.md：任务编号、需求版本、输入输出、异常、验收条件、非目标、允许修改的范围。
- context.md：仓库版本、真实文件与方法、适用规范、运行依赖、未知事项；不收集全公司资料。
- verify：公司控制的可运行校验入口、独立测试数据和预期；不得由生成代码偷偷改写。
- result：改动文件、差异、实际命令与结果、未验证事项、人工采纳/返工情况及工具用量。

规范继续以现有 AGENTS.md、README、构建文件和 CI 为准，不维护 Claude 版、Codex 版两套业务规则。
开发者提交候选实现，验证器生成实际结果，评审者判断是否可以采用；模型自己说“完成”只是候选结论。
任务合同有关键未知时先澄清；规范冲突时先修规范，不靠换工具随机选一个答案。

当前仓库已有 ai/developer-adoption/common-workflow.md，Codex 的 AGENTS.md 与 Claude Code 的 CLAUDE.md 指向同一流程。
prepare-task.mjs 为 understand、implement、repair 装配显式白名单文件与摘要，可输出文本或 JSON；它不调用模型、不执行命令、不写文件。
任务包不含参考实现、补丁和历史报告；但若把完整仓库交给 Agent，它仍可能找到答案，因此包本身不构成盲测环境。

## 3. 场景一：理解仓库，只读也能形成交付

输入任务：“解释账本汇总查询从 HTTP 入口到数据库的调用关系，本次不修改代码。”
上下文限定到实际仓库与相关文件，要求区分源码事实、合理推断和没有核实的内容。
本项目真实链路为 AccountController.summary → AccountService.ledgerSummary → AccountMapper.summarizeLedger。
输出包含这三个方法的文件位置、传入参数、返回数据和调用说明，不能编造一个不存在的服务。
人工抽查入口、中间方法及 SQL；这条链路本身不能证明完整鉴权、生产性能或所有异常已验证。
验收是引用准确、说明不越过证据，而不是文字长或架构图漂亮；记录定位加核对的总时间。

## 4. 场景二：按明确合同完成普通小需求

教学任务是规范化内部工单分页参数，仅编辑隔离 Java 样例，不连接账户、数据库或真实工单服务。
保留 TicketQuery.prepare(int page, int size, String query) 入口和既有返回结构。
page 必须 >=0；size 必须在 1..200，包含端点；非法输入抛 IllegalArgumentException，不静默归零或截断。
query 为 null 时变为空串；仅剥离首尾 Character.isWhitespace 或 Character.isSpaceChar 判定的字符，保留内部空白。
不把“去首尾空白”扩大为删除全部不可见字符；U+200B、U+FEFF 等不属于该判定的字符保持原样。
offset 使用 long 运算，不增加依赖，不附带接口改造；拒绝旧有非法输入是有意收紧行为，不能声称完全兼容。
先确认这些合同，再让工具生成实现和测试草稿；独立用例由人审定，不从候选函数反算期望值。

## 5. 场景三：先复现，再修复，再回归

同一样例中，page=2147483647、size=200，正确 offset 为 429496729400。
int 乘法先溢出后再赋给 long 会得到 -200；要在乘法前使操作数成为 long，而不是事后转换错误结果。
先在旧版保留失败断言，再做最小修改，最后执行相同测试和其他边界回归。
编译失败、JDK 缺失或运行器异常应归为环境失败，不能冒充“旧版成功复现了缺陷”。
当前固定 Java 教学对照保留三种结果：旧版 4/12，只有局部修复的候选版 5/12，完整参考版 12/12。
这些结果来自 ai/developer-adoption/workshop/verified-report.json 的 before、overflow-only、after 三个版本。
这证明单点改好并不等于整个需求完成；它不是 Claude Code、Codex 的成功率，也不是生产覆盖率。
repair 的合同仅要求 P03 转为通过、其他行为保持旧版，因此 5/12 可以满足这个窄任务；implement 要求完整 12/12，两者不能混用验收。
测试合成样本和参考版本不能证明线上接口已接入，更不能证明超大页码在真实数据库中高效。

## 6. 同一任务换工具，不改验收：一遍实际操作流程

以任务 TICKET-PAGING-01 为例，负责人冻结同一旧版本、上述合同、12 条独立用例与运行环境。
开发者甲在隔离副本中用 Codex；开发者乙在另一隔离副本中用 Claude Code，两边都从同一旧版开始。
各自先核对上下文，再生成候选补丁；禁止把完整参考答案当作输入，却宣称模型独立解决。
同一个验证入口分别检查候选文件；保留实际值、断言结果及候选文件摘要，防止结果与代码对不上。
本例选择完整 implement 任务：如果任一候选只达到 5/12，就按未满足合同退回；不删难用例，也不把另一工具的通过结果移植过来。
最终采用还要看差异质量、是否越界及人工核对成本；没有真实运行时，工具执行者字段应为空并标注教学参考。

Codex 按目录加载 AGENTS.md；先保留原规则，再确认当前工作目录与适用范围。[Codex 官方 AGENTS.md 说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
Claude Code 的入口是 CLAUDE.md，可通过其中的 @AGENTS.md 引入共享规范，避免复制两份。[Claude Code 官方项目记忆说明](https://code.claude.com/docs/en/memory)
不同工具仍需各自配置访问和执行权限；规范文件是上下文，不是沙箱，也不保证模型始终遵守。

## 7. 阶段一：先在开发者现有工具里跑通

技术负责人选定一个小组和一个仓库；产品或任务提出者确认合同；开发者负责候选修改；另一位开发者按现有评审流程复核。
第一周只做仓库定位与这个隔离练习，准备可运行依赖及人工模板基线，不接自动发布，不做后台无人值守。
开发者使用公司允许的现成 CLI 或 IDE 入口，按任务包操作，保留差异、验证结果、耗时及失败尝试。
管理员只需核实公司账号、数据发送范围和最小权限；不把生产密钥、客户数据或其他项目目录交给工具。
这时不需要网关、任务平台、向量数据库，也不需要给每个普通代码改动加多级审批。

## 8. 阶段二：重复步骤稳定后，再共享脚本

第二至四周，如果大家反复手工准备同一批资料和收集结果，就由一名开发者维护一个薄脚本。
它只负责创建隔离副本、装配任务上下文、选择工具入口、执行校验、收集差异与记录；业务合同仍只维护一份。
脚本不接受模型提供的任意目录作为写入目标，也不把模型给出的任意命令直接当公司验证入口。
结果至少记录任务/合同/代码版本、工具版本、起止时间、实际测试结果、退出状态和未验证内容；格式正确不代表事实正确。

Codex 可使用非交互模式并显式限定沙箱、记录结构化事件；不能把通用执行成功当业务测试通过。[Codex 非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)
Claude 官方建议脚本采用 --bare；该模式跳过 CLAUDE.md 等自动发现，必须显式提供经过核对的共享规则和任务上下文。
--bare 不读取交互 OAuth 或系统钥匙串，需按所选提供方配置自动化认证；不能直接沿用订阅登录。[Claude Code 程序化说明](https://code.claude.com/docs/en/headless)
自动化凭据不写入任务文件或共享日志，不让不可信构建脚本继承；不要用绕过权限的选项解决自动化阻塞。

## 9. 阶段三：确有持续批量需求，才增加 worker 平台

只有多个项目持续排队、共享脚本已稳定且人工准备确成瓶颈时，再评估工作队列和执行 worker。
每个任务使用独立工作区和任务身份，不让两个 Agent 同时改同一份工作树；同一提交的补丁仍由原有合并流程处理。
负责人给每类任务设置并发上限、最大运行时长、重试次数和费用预算；具体值依据试点记录确定，不先盲目放大并发。
运行超时就终止对应任务并保存差异，状态标为未完成；不让重试不断制造相同任务或重复写外部系统。
区分排队、运行、待人工处理、失败与完成；只有验证材料齐全且满足合同才能成为可评审候选。
读文件、改工作区、联网、创建 PR、部署分别授权；默认只交付补丁，不把“生成修复”扩张为自动合并或发布。
这层的价值是批量执行可控，不是为了拥有一个“AI 平台”；维护成本超过重复工作成本就停在共享脚本。

## 10. 负责人下周就能做什么，怎样判断值不值得继续

| 负责人 | 明确动作 | 留下的结果 |
| --- | --- | --- |
| 技术负责人 | 定一个仓库、三类任务、非目标及质量标准 | 试点清单与统一合同 |
| 模块开发者 | 修正上下文卡，核实构建与测试，保留已有规范 | 可定位源码与可运行校验 |
| 评审者 / QA | 审核独立预期，抽查候选差异和结果 | 漏检、返工、越界及可用性记录 |
| 工具管理员 | 核实账号、数据范围、自动化认证与费用归属 | 最小权限和费用责任记录 |

把澄清、查代码、提示与编写、人工评审、测试处理、返工全部计入任务总人时；失败或放弃的 AI 尝试也计入。
与相近复杂度、使用相同模板和测试的人工任务对照；另记订阅/调用费用、脚本维护和培训成本。
查看净工时、评审负担、合并后缺陷和采用情况，不把生成行数、12 条测试或模型自评分当收益。
节省的人时通常先是可用于其他工作的容量，不自动等于现金节约；没有对照数据就不承诺节约比例。
四周后决定保留哪些任务、停止哪些用法、是否需要共享脚本；升级工具时复用同一批合同与样本重新检查。

官方资料核对日期：2026-09-06。启用时核对所安装版本、公司策略与认证方式，不沿用过时参数或臆测的自动化权限。

## 11. 本仓库现在可以直接执行的部分

在完整仓库根目录，使用 Node 24 输出同一任务包；命令只读取显式来源并输出文本，不调用模型、不写文件：

```bash
node ai/developer-adoption/prepare-task.mjs understand
node ai/developer-adoption/prepare-task.mjs implement --json
node ai/developer-adoption/prepare-task.mjs repair
```

将任务包交给公司允许的 Claude Code 或 Codex 交互会话，先要求说明范围和计划，再在独立副本生成候选。CLI/SDK 的脚本接入属于后续选项；目前无需自动化认证就能先完成任务准备和本地已知样例验证。

候选生成后，在公司批准的隔离环境审查代码并运行：

```bash
node ai/developer-adoption/verify-candidate.mjs implement /path/to/candidate/TicketQuery.java --approve-local-execution
node ai/developer-adoption/verify-candidate.mjs repair /path/to/candidate/TicketQuery.java --approve-local-execution
```

路径必须指向实际候选，不能把预置参考答案当成 Agent 的交付。需要 JDK 21，报告写入随机临时目录，包含候选 SHA-256、受信测试摘要、实际值和两个分开的计数：任务验收与完整需求合同。

工具自己不是沙箱：会实际执行候选 Java，不能阻止其联网或访问文件；`--approve-local-execution` 只是操作者确认，不会建立权限隔离。公司需另行提供隔离环境，并在分享运行结果前审查敏感输出。

本次验证使用已知合成参考源码，不评价 Claude Code/Codex 的真实生成能力：完整实现通过 implement；旧版被拒绝；单溢出修复通过 repair；完整实现放进 repair 因额外改变样例行为被拒绝；编译错误、缺 JDK、未确认执行均明确失败。公司随后可把同一入口用于两种工具各自的候选，单独记录工具与模型版本。

当前已知限制：12 条固定用例不能证明未覆盖行为、源码改动范围或生产安全。任务包不是盲测环境；下载包不含完整业务源码，understand 需在完整仓库执行，implement/repair 可用包内样例。
