# 跨部门沟通案例集：需求、上线、事故和口径冲突

> 文档层级：详细实践。案例使用角色代号，重点还原真实协作中的信息、分歧、决定和产物。

## 案例一：运营要在周五晚间突然扩大流量

### 1. 初始请求

周三下午，运营在群里提出：

> 周五 20:00 有一次重要市场活动，预计流量会比较大，希望系统不要限流，最好全部放开。

这句话对研发不可执行。“比较大”没有数字，“不要限流”没有说明失败后果，“重要”也不能代替
风险判断。如果研发只回复“系统可能扛不住”，沟通会迅速变成业务与技术之间的立场冲突。

### 2. 研发先补齐事实，而不是直接拒绝

交付负责人组织 30 分钟澄清，要求运营提供：

- 推送用户数：预计 30 万；
- 用户打开率：历史约 8%—12%；
- 下单集中时间：推送后前 3 分钟；
- 单用户可能重试：最多 3 次；
- 是否叠加外部行情事件：有可能；
- 是否支持分批推送：可以按 10%、30%、60% 分三批；
- 活动暂停权限：运营负责人 O 可以执行。

研发根据历史数据给出当前证据：

- 稳定处理基线约 300 QPS；
- 受控演练覆盖 12 路同交易对并发和固定场景，不等同于生产容量证明；
- Hikari 连接池和撮合 Lane 都是有界资源；
- 系统忙时应明确返回 429/503，不能承诺永不拒绝。

### 3. 形成共同的一页说明

```text
活动目标：提高市场事件期间的有效交易参与人数
时间：周五 20:00—21:00
首要业务结果：成交唯一、资金平衡、查询最终一致

流量假设：
- 第一批 10% 用户，预计峰值 250 QPS
- 第二批累计 40%，预计峰值 650 QPS
- 第三批累计 100%，预计峰值 1200 QPS
- 用户端最多重试 3 次，必须复用 clientOrderId

系统策略：
- 保留入口和 Lane 限流
- 429 引导使用同一业务键重试
- 结算延迟不伪装成资金成功

暂停条件：
- P95 连续 5 分钟超过 800ms
- Lane 拒绝率超过 3%
- Kafka Lag 连续 10 分钟增长
- 出现重复资金效果、账本不平或对账无法收敛时立即暂停

负责人：
- 活动 O；产品规则 P；技术 A；平台 F；测试 E；最终决策 M
```

### 4. 分歧怎样解决

运营仍希望直接全量，理由是分批会损失时效。研发没有只说“不行”，而是给出三个选择：

| 方案 | 业务收益 | 技术风险 | 决定 |
|---|---|---|---|
| 一次全量 | 触达最集中 | 缺少 1200 QPS 容量证据，无法快速止损 | 不采用 |
| 10/30/60 阶梯 | 稍有延迟 | 可观察每一阶段并及时暂停 | 采用 |
| 降低活动规模 | 风险最低 | 业务收益可能不足 | 备用 |

最终由业务决策人接受阶梯放量。这个决定记录了收益和代价，后续即使活动效果不佳，也能根据
当时证据复盘，而不是追责谁“太保守”。

### 5. 这个案例解决的真实问题

- 把“比较大”变成可用于容量判断的数据；
- 把“不限流”转换成客户体验和资金风险；
- 让运营拥有暂停权，而不是事故时等待研发层层确认；
- 让研发提供替代方案，而不只是技术否定；
- 用分批策略同时保护业务机会和系统边界。

## 案例二：事故中每个部门都在说不同的“成功率”

### 1. 现场情况

活动开始 8 分钟后：

- 产品看埋点：下单按钮点击成功率 98%；
- 运营看订单后台：只有 86% 订单进入完成状态；
- 研发看接口：HTTP 2xx 为 97%；
- 测试看账本：结算完成率为 84%。

四个数字都可能正确，但它们描述的是不同阶段。如果团队继续争论“谁的数据准”，就会延误
止损。

### 2. 快速建立共同漏斗

事故指挥人将指标按业务链路排列：

| 阶段 | 数量 | 比例 | 解释 |
|---|---:|---:|---|
| 点击下单 | 10,000 | 100% | 用户行为 |
| API 已接受 | 9,700 | 97% | 不等于成交 |
| 形成成交 | 9,100 | 91% | 部分订单因无流动性拒绝 |
| 结算完成 | 8,400 | 84% | 700 条等待 Kafka 消费 |
| 资金可见 | 8,380 | 83.8% | 20 条等待查询投影同步 |

共同结论：入口没有大面积失败，主要问题是结算积压，另有少量查询同步延迟。HTTP 2xx 不能被
当成最终业务成功率。

### 3. 第一次事故更新

```text
时间：20:10
影响：约 700 笔已成交订单等待结算，另有约 20 笔资金结果暂未同步到查询页。
正确性：目前未发现重复入账或账本不平。
已确认：入口和撮合正常，Kafka 结算积压上升。
动作：暂停第三批推送；平台检查消费者和数据库等待；研发核对 Inbox 与账本。
下一决定：20:20 前 Lag 未下降则结束本次活动。
下一更新：20:15，事故沟通负责人 O。
```

这条消息同时满足管理层、产品、运营和研发需要。它没有把未知信息写成事实，也没有只发技术
指标。

### 4. 无效沟通对照

```text
Kafka 有点积压，我们还在看，服务本身是好的，大家先别急。
```

问题在于：没有客户影响、没有数量、没有动作、没有暂停条件、没有下一次更新时间。“服务是
好的”还可能与用户实际等待相冲突。

### 5. 恢复不能只看 Lag 清零

20:18 Kafka Lag 下降到 0。事故指挥人没有立即宣布恢复，而是完成三层确认：

1. 系统层：消费者、数据库连接和延迟恢复；
2. 数据层：Inbox 数量、账本借贷和平衡状态正确；
3. 业务层：完成率恢复，对账为 CLEAN，产品确认用户资金可见。

20:22 才恢复第二批流量，第三批取消。这个决定避免“技术指标恢复但客户结果仍错误”。

## 案例三：需求开发到一半，产品修改核心规则

### 1. 变化

原需求规定：市场深度耗尽时，市价单剩余数量直接进入 `REJECTED`。开发完成一半后，产品希望
改为“剩余部分保留，等待新深度继续成交”。

这不是文案变化，而是订单生命周期和客户资金占用规则变化。研发如果直接说“改不了”，产品
会认为技术不支持业务；如果为了进度直接修改，又可能破坏订单守恒和结算逻辑。

### 2. 研发给出影响说明

```text
变化影响：
- 订单新增 PARTIALLY_FILLED 后继续等待的生命周期
- 客户可用余额需要持续冻结
- 取消、超时和新深度到达规则需要补充
- 撮合恢复、消息重放和查询展示均需调整
- 现有“无深度明确拒绝”自动测试不再适用

选择 A：本期保持 REJECTED，下期完整设计挂起逻辑
选择 B：本期修改，发布日期延后两周并补齐资金冻结与取消规则
选择 C：只修改页面文案但不改行为——不建议，会误导客户
```

### 3. 决策

产品确认本次活动并不依赖挂起订单，选择 A。双方记录下一期要验证的用户价值，而不是把需求
变化变成研发团队的隐性返工。

### 4. 关键经验

- 研发用业务链路解释成本，而不是用类和表结构解释；
- 产品明确变化带来的价值和时间要求；
- 决策人选择范围、时间、风险组合；
- 测试保留原有不变量，不为赶进度模糊期望。

## 案例四：运营反馈“有用户说钱没到账”

### 1. 无结构反馈的风险

运营在群里转发一句：“有用户说成交后钱没到账，比较着急。”研发无法判断是个例、查询延迟、
结算积压、真实资金错误还是用户看错账户。

### 2. 使用统一反馈单

```text
反馈时间：14:05
用户场景：卖出 CRASH-USDT 后查看余额
订单标识：已脱敏的 orderId / clientOrderId
成交时间：13:58:21
用户看到：成交记录存在，USDT 可用余额未变化
影响范围：当前 3 个相同反馈，均来自同一活动批次
临时处理：告知用户正在核查，15 分钟后更新
相关证据：页面截图、活动批次、查询时间
```

### 3. 研发排查顺序

1. 权威成交是否存在；
2. 结算命令是否进入 Outbox/Kafka；
3. Inbox 与 settlement 状态；
4. 账本事务是否平衡；
5. 余额是否已更新；
6. 查询投影是否缺失或延迟。

最终发现账本和余额正确，是查询投影 `MISSING`。团队重建投影并确认 CLEAN，不修改权威成交或
历史账本。运营得到可向用户解释的结论，而不是一句“后端数据正常”。

## 案例五：两个部门对同一个指标的定义不同

### 1. 分歧

产品把“交易成功率”定义为形成成交的订单数除以提交订单数；运营排除了用户主动取消和无流动性
拒绝；研发把接口接受率当作成功率。三方月报无法对齐。

### 2. 指标字典

| 指标 | 统一定义 | 数据源 | 负责人 | 注意事项 |
|---|---|---|---|---|
| 订单接受率 | API 接受且持久化的订单 / 合法提交 | order 表、入口指标 | 研发 | 不等于成交 |
| 成交率 | 产生至少一笔成交的订单 / 已接受订单 | 权威 trade/order | 产品 | 受市场深度影响 |
| 结算完成率 | 成功结算业务 / 应结算业务 | settlement、ledger | 研发 | 必须同时验证账本 |
| 资金可见率 | 用户查询已展示正确余额 / 已结算业务 | 余额与查询投影 | 产品 | 受同步延迟影响 |
| 活动有效转化 | 满足运营资格且完成目标行为的用户 / 触达用户 | 活动平台与业务事实 | 运营 | 排除规则要版本化 |

指标字典注明版本和生效时间。以后报表仍可展示不同阶段，但不能再用同一个“成功率”名称描述
不同事实。

## 六、跨部门会议的真实议程样例

### 需求澄清会，45 分钟

```text
会前输入：一页需求说明、用户数据、活动计划
0—10 分钟：产品说明用户问题和目标指标
10—20 分钟：运营说明时间、流量和现场处置
20—35 分钟：研发、测试提出边界、失败路径和依赖
35—42 分钟：处理需要决定的分歧
42—45 分钟：复述决定、负责人、期限和未决问题
```

### 上线准备会，30 分钟

```text
不重复讲需求背景，只检查：
- 自动验收是否通过
- 容量和流量阶梯是否确认
- 监控、告警、回滚和权限是否可用
- 客户文案和运营暂停入口是否准备
- 谁在什么时间做继续、暂停或回滚决定
```

### 复盘会，60 分钟

```text
0—15 分钟：基于证据还原时间线
15—30 分钟：区分触发、放大和恢复障碍
30—45 分钟：讨论技术、流程、信息和能力缺口
45—55 分钟：确定行动项和验收证据
55—60 分钟：确认对外结论和复查时间
```

## 七、跨部门协作产物检查表

- [ ] 有一份共同目标和范围说明；
- [ ] 业务不变量和异常表现明确；
- [ ] 产品、运营、研发、测试负责人明确；
- [ ] 流量与容量假设有数字和来源；
- [ ] 上线、暂停、回滚和恢复条件明确；
- [ ] 重要分歧有决策记录；
- [ ] 事故信息包含影响、动作和下次更新时间；
- [ ] 指标名称有统一定义和数据源；
- [ ] 上线后产品与运营共同确认业务结果；
- [ ] 改进行动具备负责人、期限和验收证据。

## 结语

真实的跨部门沟通不是说服别人接受本部门方案，而是把模糊请求转换成共同事实，把立场冲突
转换成可选择的收益与风险，把事故噪声转换成一致行动。案例可以不同，但共同目标、角色、指标、
决定和验证这五个工作对象应保持稳定。
