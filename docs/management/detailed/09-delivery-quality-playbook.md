# 交付效能与质量治理实战

## 一、场景：六个项目同时“最高优先级”

团队同时收到网站交互、认证授权、Kafka DLT、灾备、性能认证和新撮合规则六项要求。每项单独看
都合理，但领域负责人和测试被重复占用，最终所有项目都延期，稳定性任务最先被牺牲。

技术负责人把项目放到同一张组合看板，按业务结果、客户影响、风险降低、时间窗口、依赖和投入
比较，而不是逐个会议分别承诺。

## 二、项目组合看板

| 项目 | 结果 | 保护指标 | 关键依赖 | 容量 | 决定 |
|---|---|---|---|---:|---|
| 实验接口隔离 | 公网演示风险下降 | 演练仍可在隔离环境运行 | 安全设计 | 2 人月 | 本季度完成 |
| 灾备基线 | 证明备份可恢复 | 不修改权威数据 | 基础设施 | 1.5 人月 | 本季度完成 |
| Kafka DLT | 毒消息可审核重放 | 不产生重复资金效果 | 结算负责人 | 1 人月 | 下一里程碑 |
| 新撮合规则 | 扩展产品能力 | 不破坏价格时间优先 | 产品规则 | 2 人月 | 推迟到规则确定 |
| 网站交互优化 | 更容易理解项目 | 不影响 API 演示 | 前端 | 0.5 人月 | 小步交付 |
| 性能认证 | 给出容量结论 | 不宣传单次峰值 | 目标环境 | 1 人月 | 灾备后开始 |

新增紧急项目必须明确替换哪一项，不能只在原计划上叠加。

## 三、交付一页说明

```text
业务问题：公网演示接口与实验故障接口边界不够清晰
目标结果：公开访问者只能运行受控场景，不能直接修改故障状态
成功指标：未授权高风险调用全部拒绝；受控演示成功率保持
保护指标：金融不变量、演示延迟、部署复杂度
不在范围：真实客户身份、支付级合规认证
依赖：角色定义、环境隔离、前端调用方式
灰度与回滚：先影子记录，再强制；保留上一版本回滚
负责人：安全设计 A；应用实现 C；产品验收 P
```

## 四、DORA 与业务指标样例

| 指标 | 口径 | 用途 | 禁止用法 |
|---|---|---|---|
| 部署频率 | 成功进入目标环境的发布 | 判断交付批量 | 比较个人速度 |
| 交付周期 | 提交到成功发布的中位数/P95 | 发现等待与批量 | 要求所有任务同周期 |
| 变更失败率 | 需回滚、修复或造成客户影响的发布 | 判断发布质量 | 隐藏失败或减少发布 |
| 恢复时间 | 影响开始到业务确认恢复 | 改善检测和恢复 | 只看服务重启时间 |
| 资金正确性 | 重复效果、账本不平、未授权修改 | 守住业务底线 | 与普通缺陷平均 |

每月看趋势和原因，不根据一次波动做绩效结论。

## 五、风险分级发布

### L1 低风险

文档、展示文本、无状态低影响修改。自动测试通过，可由领域成员发布。

### L2 中风险

查询、监控、可回滚配置。需要领域评审、监控、灰度和回滚验证。

### L3 高风险

资金事务、权限、数据库迁移、消息语义。需要双人评审、关键场景测试、安全/数据检查、业务与
运行确认、明确观察窗口。

### L4 重大风险

不可逆数据操作、核心架构迁移、大流量活动和灾备切换。需要技术负责人最终负责，跨部门彩排，
管理决策和独立证据。

## 六、发布门禁样例

```text
[ ] 业务目标和失败状态已确认
[ ] 金融不变量和安全边界已标注
[ ] 自动测试、迁移和回滚验证通过
[ ] 容量与依赖满足目标流量
[ ] 监控、告警和客户/运营口径就绪
[ ] 值班、决策人和最晚回滚时间明确
[ ] 发布后业务验收负责人在线
```

## 七、质量策略：以风险为中心

| 风险 | 主要验证 |
|---|---|
| 重复消息造成重复资金效果 | 唯一约束、Inbox、并发集成测试 |
| 旧 Worker 恢复写入 | 事务内 Fence、接管竞态测试 |
| 查询投影错误 | MISSING/MISMATCH/EXTRA 对账和修复边界 |
| 数据库迁移失败 | Testcontainers 迁移、回滚或前向修复策略 |
| 权限绕过 | 角色矩阵、接口级拒绝和审计 |
| 容量过载 | 固定到达率、保护指标和降级验证 |

## 八、延期诊断案例

“认证授权延期两周”背后可能是：角色规则未由业务决定、所有评审集中在 A、测试环境没有身份
服务、成员缺少 Spring Security 经验。对应动作分别是提前产品决策、授权备份评审、提供隔离替代、
安排结对与缩小第一阶段，而不是统一要求周末加班。

## 九、周交付评审

会议只查看：目标偏差、客户/生产影响、最晚决定、依赖风险、范围变化、发布准备。正常任务进度
异步更新。出现连续等待时解决系统瓶颈，避免反复催促执行者。

## 十、验收标准

- 团队有一张跨项目的真实优先级与容量视图；
- 新项目会替换既有投入，而不是无限叠加；
- DORA、业务和正确性指标一起使用且不评价个人；
- 发布流程随风险分级；
- 延期能够定位到范围、依赖、能力、质量或资源原因；
- 交付以业务和运行验收结束。
