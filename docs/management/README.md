## 为什么技术项目还需要管理体系

金融可靠性项目的问题很少只发生在代码里。一次线上事故可能同时涉及产品规则不完整、
运营活动流量预估不足、研发对边界理解不一致、测试只验证正常路径、值班信息没有及时同步。
如果团队仍然依赖少数骨干临时协调，即使撮合、结算、Outbox、幂等和 Epoch Fencing 都实现
正确，组织层面依然可能成为系统可靠性的短板。

本手册把 FinCore Reliability Lab 中已经验证的工程方法转换成团队管理方法：

- 用明确的不变量统一目标，避免不同部门各自解释“成功”；
- 用角色备份和故障演练降低关键岗位单点风险；
- 用事实、指标和决策记录代替口头同步；
- 用产品、运营、研发共同验收的业务结果结束需求，而不是以“代码上线”结束；
- 用复盘和能力认证推动团队成长，而不是只靠培训次数衡量提升。

## 统一原则

### 1. 结果优先于动作

“完成开发”“执行压测”“发出通知”都只是动作。最终要回答的是：业务结果是否唯一、资金是否
平衡、客户是否受到影响、运营是否能观察和处置、产品是否达到预期指标。

### 2. 关键知识必须有冗余

撮合、结算、账本、对账、基础设施等关键领域都应至少有一名负责人、一名备份和一名正在培养
的成员。负责人不是知识所有者，而是知识传播和风险收敛的责任人。

### 3. 决策必须留下证据

重要决定应记录背景、选择、代价、负责人和复查时间。指标、代码、测试、演练记录和用户反馈
都是证据；“大家当时都同意”不是可审计的决策记录。

### 4. 风险要在上线前讨论

跨部门评审不仅讨论要做什么，还要讨论什么不能发生、系统忙时如何表现、怎样回滚、谁有权
暂停活动，以及出现异常后多久进行下一次信息同步。

### 5. 复盘服务于改进而非归责

复盘的产出不是找到一个犯错的人，而是识别哪些系统、流程、信息和能力缺口让错误可以发生，
并把改进项落实到负责人、期限和验收证据。

## 建议使用方式

- 管理者先使用第五篇建立最小会议和指标节奏；
- 技术负责人依据第一、二篇建立领域负责人和能力矩阵；
- 项目经理或交付负责人依据第三篇统一跨部门输入和决策记录；
- 产品、运营和研发共同使用第四篇完成需求定义、上线准备和结果复盘；
- 每季度根据真实事件修订手册，避免文档与团队实际工作脱节。

这些内容不是固定的人事制度，也不直接对应职级和绩效等级。团队应结合人数、业务阶段、监管
要求和组织分工调整，但不应弱化结果可验证、关键知识有备份和风险提前暴露这三条底线。
