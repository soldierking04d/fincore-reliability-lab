# 公开内容发布边界

公开仓库与项目展示站只承载项目本身及可核验的交付能力：

- 业务问题、系统架构、代码实现、测试数据、失败契约和真实限制；
- 面向产品、运营、技术与管理协作的客观说明；
- 团队招聘、入职培养、绩效反馈等组织管理流程，但不包含个人准备答案；
- 标明环境与证据等级的演示、测量和复现步骤。

个人准备材料、第一人称应答脚本和针对评审者的表达训练不属于公开内容。此类材料应保存在公开仓库之外，
不得以隐藏页面、折叠区块、注释、数据文件或未链接文档等形式随站点或 Git 提交发布。

## 提交与发布检查

1. 检查新增或改动文件的实际内容，而不仅是标题、菜单和可见页面。
2. 技术问题应写成业务约束、设计决策、失败路径和验收事实，不将个人应答稿仅改标题后保留。
3. 校验文档、站点、下载文件及源码注释，确保移出材料后不存在旧入口与断链。
4. 保留真实能力边界，不能为了展示效果把设计、实验或第三方资料写成已完成的生产实现。
5. 发布前运行公开内容门禁，并对管理内容的例外清单进行人工复核。

```bash
bash scripts/verify-public-content.sh --self-test
bash scripts/verify-public-content.sh
```

门禁扫描所有已跟踪文本及路径。团队管理例外仅限三个明确文件中的六条既有原句，
不豁免整个文件或目录；违规日志只列位置，不复述原文。脚本是防回归保障，不替代语义审查；
含义相同但措辞不同的个人材料仍应人工移出。

历史版本、第三方缓存和已克隆内容不能通过一次普通提交撤回。修改公开分支与在线资源不会自动改写历史，
需要清除历史时应另行评估协作影响和授权范围。
